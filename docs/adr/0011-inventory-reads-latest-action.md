# Inventory's list and detail read the latest action with read-only SQL

§4.2 says `dashboard` is the only module that reads across tables, yet §4.4 and §4.7 give the `inventory` list and detail a `LEFT JOIN LATERAL` on `vehicle_action` for `currentAction` and the `hasAction` filter. We keep the §4.4 query: `inventory` reads `vehicle_action` in the same read-only SQL statement and imports nothing from the `actions` module, so the module graph gains no edge and no cycle, and writes still belong to the owning module only. The rule becomes: only the owning module writes a table; cross-table reads are read-only SQL, and only where the design names them (`dashboard`; `inventory` list and detail → latest action). Attaching the action in the `actions` module after the query was rejected because `hasAction` with `limit`/`offset` would then filter after paging, giving short pages and a wrong `total`. Moving list and detail into `dashboard` was rejected because it splits vehicle reads from the module that owns the vehicle.
