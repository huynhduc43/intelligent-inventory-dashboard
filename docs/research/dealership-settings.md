# Dealership settings building blocks (research for #14)

Research for issue #14 (`GET`/`PATCH /api/v1/dealerships/{d}/settings`; §4.2, §4.7, D3, ADR 0004, ADR 0005, ADR 0007, ADR 0010). The routes, the permissions (`settings:read`, `settings:update`), the body `{timezone?, watchDays?, agingDays?}` and the codes `422 THRESHOLDS_INVALID`/`TIMEZONE_INVALID` are taken as given. Where `validateThresholds` lives (the issue's open question) is not covered here. Five findings shape the design. (1) An exact `name = $1` match against `pg_timezone_names` is case-sensitive and accepts only canonical tzdb names, but it costs about 9–10 ms because the view reads every zone file on each call. `AT TIME ZONE` is much looser: it accepts any case, abbreviations (`PST`) and POSIX strings (`UTC+5`, `foo+3`). So "evaluate it and catch `22023`" is cheaper but does not prove the value is an IANA name. (2) Four listed names (`CET`, `EET`, `MET`, `WET`) are shadowed by abbreviations inside `AT TIME ZONE`, so they evaluate as fixed offsets without DST. (3) A `CHECK` violation from an `UPDATE` surfaces exactly like the VIN `23505` did: a `DrizzleQueryError` with the pg `DatabaseError` (`code '23514'`, `constraint`) on `.cause`. Today it becomes a 500. Two concurrent PATCHes can each pass an app-side check and still violate `dealership_thresholds_chk` together, so the CHECK is the real guard. (4) RFC 5789 requires PATCH to be atomic. With a plain JSON body, absent members are left unchanged, so `{}` is a no-op that returns 200 with the current settings. (5) The repo has no 422, and no coded exception that carries `errors[]`, yet.

Method: claims were checked against the PostgreSQL 17 docs, the PostgreSQL `REL_17_STABLE` source (`src/backend/utils/adt/datetime.c`, `src/timezone/pgtz.c`, fetched from GitHub), RFC 5789, RFC 7396 and RFC 9110, and the installed packages (`drizzle-orm@0.45.4`, `pg@8.23.1`). The probes were throwaway scripts kept in the scratchpad. They ran against a separate `postgres:17.11-alpine` container (the image used by `docker-compose.yml` L4 and `apps/api/test/integration/support/postgres.ts` L10) with the committed migrations applied, through `psql` and through `drizzle-orm/node-postgres` from `apps/api`. Line numbers refer to the files of the version named.

## 1. Validating the time zone

### What `pg_timezone_names` lists and how it matches

- **Source of the list.** The view lists "time zone names that are recognized by `SET TIMEZONE`" ([52.32 pg_timezone_names](https://www.postgresql.org/docs/17/view-pg-timezone-names.html)). It is backed by the set-returning function `pg_timezone_names()`, which "reads all the available full time zones" (`datetime.c` L5118-L5144). It walks the tzdata directory with `pg_tzenumerate_start`/`_next`, calls `tzload()` on every file, skips leap-second zones and returns "the canonical zone name spelling" (`pgtz.c` L397-L495). The image is built `--with-system-tzdata=/usr/share/zoneinfo` (`pg_config --configure`), so the list is whatever the image's tzdata package contains. Probe: 599 names, 35 under `Etc/`, none under `posix/` (that directory does not exist in the image), and `Factory` and `posixrules` are listed.
- **Exact match is case-sensitive.** `name` is plain `text`, so `WHERE name = $1` is an ordinary byte comparison. Probe (`exists(… where name = n)`):

  | Input                                                     | Listed |
  | --------------------------------------------------------- | ------ |
  | `Europe/London`, `UTC`, `Etc/UTC`, `GMT`, `EST`, `Zulu`   | yes    |
  | `EST5EDT`, `Etc/GMT+5`, `US/Eastern`, `Asia/Saigon`       | yes    |
  | `europe/london`, `EUROPE/LONDON`, `utc`                   | no     |
  | `PST`, `UTC+5`, `+05`, `posix/Europe/London`, `localtime` | no     |
  | `Not/AZone`, `''`                                         | no     |

  No two listed names differ only in case (probe: 0 rows), so a case-insensitive match (`lower(name) = lower($1)`) would be unambiguous if friendlier input were wanted. It would then store the canonical `name`.

- **Cost.** Because the function loads every zone file on each call, it is not cheap. Probe (`EXPLAIN ANALYZE`): `Function Scan on pg_timezone_names` took 8.6 ms for a hit and 10.3 ms for a miss (`Rows Removed by Filter: 599`). By comparison, `now() AT TIME ZONE 'Europe/London'` took 0.23 ms, because `pg_tzset` caches loaded zones per backend (`pgtz.c` L234-L300). That is fine for a rare admin write, but it should not run on every request.

### What `AT TIME ZONE` accepts

- **Lookup order.** `DecodeTimezoneName` lowercases the input and looks it up in the abbreviation table first. Only if that fails does it call `pg_tzset` as a full zone name, and an unknown name raises `ERRCODE_INVALID_PARAMETER_VALUE` "time zone \"%s\" not recognized" (`datetime.c` L3190-L3235). `pg_tzset` upper-cases the name for a case-insensitive cache lookup, and if no zone file matches it falls back to `tzparse()` as a POSIX spec (`pgtz.c` L234-L290).
- **The docs agree.** The docs list three accepted forms: a full name, an abbreviation (which "merely defines a particular offset from UTC" and can be used "with the `AT TIME ZONE` operator") and a POSIX-style spec. They add that "timezone names and abbreviations are recognized case-insensitively" ([8.5.3 Time Zones](https://www.postgresql.org/docs/17/datatype-datetime.html#DATATYPE-TIMEZONES)). For POSIX specs: "The positive sign is used for zones _west_ of Greenwich", and "it is easy to misspell a POSIX-style time zone specification, since there is no check on the reasonableness of the zone abbreviation(s). For example, `SET TIMEZONE TO FOOBAR0` will work" ([B.5](https://www.postgresql.org/docs/17/datetime-posix-timezone-specs.html)).
- **Probe** (`timestamptz '2026-07-01 23:30Z' AT TIME ZONE $z`):

  | `$z`                                                                      | Result                                             |
  | ------------------------------------------------------------------------- | -------------------------------------------------- |
  | `Europe/London`, `europe/london`, `EUROPE/LONDON`                         | `2026-07-02 00:30` (all three accepted)            |
  | `utc`                                                                     | `2026-07-01 23:30`                                 |
  | `PST` (not listed)                                                        | `15:30` (abbreviation, fixed −8)                   |
  | `UTC+5`, `+05`, `XYZ5` (not listed)                                       | `18:30`, i.e. UTC−5 (POSIX sign: positive is west) |
  | `foo+3` (not listed)                                                      | `20:30`                                            |
  | `Factory` (listed)                                                        | `23:30`                                            |
  | `posix/Europe/London`, `localtime`, `Not/AZone`, `''`, `'Europe/London '` | `ERROR 22023: time zone "…" not recognized`        |

  So `AT TIME ZONE` accepts a strict superset of the listed names. Catching `22023` would let `UTC+5` (which means UTC−5) and misspellings like `foo+3` be stored as a dealership's zone.

- **Every listed name is accepted.** A `DO` loop over all 599 names ran `now() AT TIME ZONE name` with 0 failures.
- **But some listed names mean something else in `AT TIME ZONE`.** Because abbreviations are checked first, a listed name that is also an abbreviation evaluates as the abbreviation. Listed names that collide with `pg_timezone_abbrevs` (case-insensitive): `CET, EET, EST, GMT, HST, MET, MST, UCT, UTC, WET, Zulu`. For most of them this makes no difference, because the zone is a fixed offset anyway. For `CET`, `EET`, `MET` and `WET` it does: probe at 2026-07-01 23:30Z, `AT TIME ZONE 'CET'` gives `00:30` (fixed +1) while `Europe/Paris` gives `01:30` (+2, summer time). A dealership stored as `CET` would never see DST.

### Where the check should run, and why it matters

- `DealershipGuard` evaluates `($now::timestamptz AT TIME ZONE d.timezone)::date` on every dealership request (`apps/api/src/modules/auth/dealership.guard.ts` L52-L58). A stored value that `AT TIME ZONE` rejects makes every request to that dealership fail with `22023`, which the filter maps to 500 (`apps/api/src/shared/problem.ts` L139-L143). ADR 0004 already places the check in the dealerships module on write, and `schema.ts` L27 says the same. The column itself is plain `text` (L28).
- **One statement for both the check and the write.** The guard has already proved that the dealership exists and that the caller is a member, so the existence test can sit in the `UPDATE`'s `WHERE`, where zero rows means `TIMEZONE_INVALID`:

  ```sql
  UPDATE dealership
  SET timezone   = COALESCE($tz, timezone),
      watch_days = COALESCE($watch::smallint, watch_days),
      aging_days = COALESCE($aging::smallint, aging_days)
  WHERE id = $d
    AND ($tz::text IS NULL OR EXISTS (SELECT 1 FROM pg_timezone_names WHERE name = $tz))
  RETURNING name, timezone, watch_days, aging_days,
            (($now::timestamptz AT TIME ZONE timezone)::date)::text AS today_local
  ```

  Probe through drizzle: `$tz = 'europe/london'` → `rowCount 0`. All three parameters null → one row with the values unchanged. `RETURNING` sees the new row, so `todayLocal` is computed in the new zone, as the "Node never does time-zone maths" rule requires ([UPDATE](https://www.postgresql.org/docs/17/sql-update.html): `RETURNING` is computed "based on each row actually updated").

- **Upgrades of the tzdata.** The accepted set is whatever tzdata the image ships with, so a future tzdata that dropped a stored name would turn that dealership's requests into 500s. IANA normally keeps renamed zones as links (`Asia/Saigon` and `US/Eastern` are still listed), so this is a note for image upgrades, not something to build now.

## 2. A `CHECK` violation (`23514`) through drizzle

- **Wrapping.** It is the same mechanism `vehicle-intake.md` §2 described for `23505`. `NodePgPreparedQuery.execute` runs inside `queryWithCache`, which with no cache configured catches the error and throws `new DrizzleQueryError(queryString, params, e)` (`drizzle-orm/pg-core/session.js` L36-L42). `DrizzleQueryError` keeps the driver error as `cause` (`drizzle-orm/errors.js` L10-L21).
- **Probe** (`UPDATE dealership SET watch_days = COALESCE(100, watch_days), aging_days = COALESCE(null, aging_days) …` with aging 90): `e instanceof DrizzleQueryError === true`, `e.code === undefined`, `e.cause instanceof pg.DatabaseError === true`, `e.cause.code === '23514'`, `e.cause.constraint === 'dealership_thresholds_chk'`, `e.cause.table === 'dealership'`. An unknown zone in `AT TIME ZONE` surfaces the same way, with `e.cause.code === '22023'`.
- **How the repo maps pg errors today: it does not.** There is no catch of `DrizzleQueryError` anywhere in `apps/api/src` (grep for `23505`, `23514`, `DrizzleQueryError` finds nothing). The VIN conflict is avoided with `ON CONFLICT … DO NOTHING` and a 0-row check (`apps/api/src/modules/inventory/vehicles.service.ts` L80-L93), and status changes use a conditional `UPDATE` with a re-read (L105-L123). Every other thrown value becomes `500 INTERNAL` (`problem.ts` L139-L143).
- **The constraint** is `watch_days >= 1 AND watch_days < aging_days AND aging_days <= 3650` (`apps/api/src/shared/schema.ts` L33-L36), the D3 rule.
- **The race that only the CHECK catches.** An app-side `validateThresholds` would run on the merged pair (the patch plus the guard's `watchDays`/`agingDays`), and those values can be stale. Probe: session A ran `UPDATE … SET aging_days = 70` and held its transaction open for 2 s. Session B ran the `COALESCE` update with `watch_days = 80`. B's app-side check would pass against 60/90. B waited 1.49 s, then failed with `ERROR 23514 … DETAIL: Failing row contains (…, 80, 70)`. Postgres re-applies B's `SET` to A's committed row, so the `COALESCE` form keeps A's `aging_days` and the CHECK sees the real pair. Final row: 60/70. So the app-side check gives the friendly 422 in the normal case, and the CHECK, mapped to the same 422, covers the race. Without the mapping the race is a 500.
- **The DETAIL contains the row.** Never put `cause.detail` or `cause.message` into the problem `detail`. The filter's 500 path does not (`problem.ts` L139-L143), and a 422 mapping should use a fixed message.
- **The SQL bound.** The columns are `smallint` (`schema.ts` L29-L30). Any value above 32767 raises `22003` before the CHECK runs, so the validation must bound the inputs before SQL. `validateThresholds` rejecting anything outside `1 … 3650` does this.

## 3. PATCH semantics for a plain JSON body

- **Atomic.** "The server MUST apply the entire set of changes atomically and never provide (e.g., in response to a GET during this operation) a partially modified representation. If the entire patch document cannot be successfully applied, then the server MUST NOT apply any of the changes" ([RFC 5789 §2](https://www.rfc-editor.org/rfc/rfc5789#section-2)). A single `UPDATE` statement satisfies this. An invalid zone together with valid thresholds must change nothing, and the `WHERE` form above does exactly that.
- **Absent fields.** The body is `application/json` with optional members, not `application/merge-patch+json`. RFC 7396 is still the closest standard: absent members leave "the remaining content untouched", and `null` means "removal of existing values" ([RFC 7396 §1](https://www.rfc-editor.org/rfc/rfc7396#section-1)). None of the three settings can be removed (all columns are `NOT NULL`, `schema.ts` L28-L30), so `null` should be refused with `400 VALIDATION_FAILED` (`.optional()`, not `.nullish()`).
- **Empty body `{}`.** In the RFC 7396 algorithm an empty patch has no pairs to apply and returns the target unchanged (§2). So `{}` is a valid no-op: return 200 with the current settings. The `COALESCE` statement with all nulls already does this. Rejecting `{}` with 400 is defensible, but no RFC requires it.
- **Response.** RFC 5789's example answers 204, and "other success codes could be used as well" (§2.1). §4.7 fixes `PATCH … → settings`, so the response is 200 with the same body as `GET` (`{name, timezone, watchDays, agingDays, todayLocal}`), and `todayLocal` comes from `RETURNING` in the new zone.
- **422.** "The server understands the content type of the request content … and the syntax of the request content is correct, but it was unable to process the contained instructions" ([RFC 9110 §15.5.21](https://www.rfc-editor.org/rfc/rfc9110#name-422-unprocessable-content)); RFC 5789 §2.2 names 422 for a well-formed patch that cannot be applied. This matches the §4.8 split: 400 for shape, 422 for meaning (a pair out of order, an unknown zone).
- **Caching.** "A response to this method is only cacheable if it contains explicit freshness information … as well as the Content-Location header" (RFC 5789 §2). The existing `PATCH …/status` sets no `Cache-Control` (`vehicles.controller.ts` L255 onward), so only the `GET` needs `no-store`.
- **Idempotency.** RFC 5789 §2 says PATCH "is neither safe nor idempotent" in general. This one is idempotent (it sets absolute values), and `If-Match` is deferred (§6), so the last writer wins on any field it sends.

## 4. House patterns the new module should follow

- **Module and routes.** One module per table owner, with the controller at `@Controller('dealerships/:dealershipId/…')` and `@ApiTags`/`@ApiBearerAuth` (`apps/api/src/modules/dashboard/dashboard.controller.ts` L111-L114; `dashboard.module.ts`). It is registered twice in `AppModule`: once in `RouterModule.register([{ path: 'api/v1', module: … }])` and once in `imports` (`apps/api/src/app.module.ts` L30-L41). The comment at L30 already expects the dealership modules.
- **Guard and context.** `@RequirePermission('settings:read' | 'settings:update')` applies `DealershipGuard` (`apps/api/src/modules/auth/decorators.ts` L13), which fills `req.dealershipId` and `req.dealership` with `{role, timezone, watchDays, agingDays, todayLocal}` (`dealership.guard.ts` L66-L73). Each controller has a small `context(req)` helper that throws if the guard did not run (`vehicles.controller.ts` L97-L103, `dashboard.controller.ts` L145). `GET` still needs one query for `name`, which is not in the context.
- **`Cache-Control: no-store`** is set with `@Header('Cache-Control', 'no-store')` on each read route (`vehicles.controller.ts` L113, L224; `dashboard.controller.ts` L119; `actions.controller.ts` L122; `auth.controller.ts` L40, L73). `todayLocal` changes at local midnight, so the settings `GET` needs it too.
- **Body validation (ADR 0005).** A module-level `z.strictObject` passed as `@Body({ schema })` (`vehicles.body.ts` L4, L30; `actions.controller.ts` L33, L105), plus `@Query({ schema: noQuery })` on routes that take no query (`vehicles.controller.ts` L293, `apps/api/src/shared/query.ts` L3). The global pipe maps issues to `400 VALIDATION_FAILED` with `errors[{pointer, message}]` (`apps/api/src/shared/shared.module.ts` L37-L38, `problem.ts` L62-L74). Free text goes through `text()` from `shared/text.ts` (refuses U+0000, ADR 0004). That covers `timezone`, since a U+0000 would otherwise raise `22021`, a 500.
- **Coded errors (ADR 0007).** `throw new CodedHttpException(status, CODE, message)` (`problem.ts` L31-L39). It is used for `401 INVALID_CREDENTIALS`, `409 VIN_ALREADY_IN_STOCK`, `409 INVALID_TRANSITION` and the actions 409 (`auth.service.ts` L34, `vehicles.service.ts` L88, L119, `actions.service.ts` L67). **No 422 exists yet, and no coded exception carries `errors[]`.** `describeException` attaches `errors` only for `ValidationFailedException` (`problem.ts` L114-L121, L133-L137), although `buildProblem` already accepts them (L86-L101) and §4.8's example shows `errors` on a coded 409. A 422 with `errors[{pointer: '/watchDays'}]` therefore needs `CodedHttpException` to take optional `errors` and `describeException` to pass them through. A 422 with only `code` and `detail` needs no change.
- **OpenAPI (ADR 0010).** zod request bodies reach the document with no extra decorator. Responses are hand-written `SchemaObject`s with `@ApiOkResponse` and one `@ApiResponse({status, description, content: problemRef})` per error (`vehicles.controller.ts` L35-L89, L132-L160, L259-L289). After adding routes, run `pnpm --filter @inventory/api openapi:export` (`apps/api/package.json` L16) to regenerate `docs/api/openapi.json`, and add the new path to the expected list in `apps/api/test/integration/openapi.spec.ts` L30-L41. The first test there fails until the export is committed (L26-L28).
- **Route × role test.** `rbac.spec.ts` has a probe controller per permission plus a §4.6 `MATRIX` (L24-L90, "Later issues add their real routes as rows of the table below"). Real GET routes are entries in the `suffix` list (L142-L147), checked by "every role 200, non-member 404, no token 401" (L151-L160) and "non-member 404 body equals the missing-dealership body" (L242 onward). Real writes each get their own `it`, for example `PATCH status: admin and manager 200, viewer 403, non-member 404 with the missing-dealership body, no token 401` (L186-L208). Settings needs `'settings'` added to `suffix`, and a `PATCH settings` test with admin 200, manager 403, viewer 403, non-member 404 (three bodies identical), and no token 401. Use a body that changes nothing harmful, such as `{}` or the current values, because the suite shares one seeded database.

## Decisions this implies

1. Validate `timezone` with an exact `name = $1` match in `pg_timezone_names`, inside the `UPDATE`'s `WHERE`. Zero rows means `422 TIMEZONE_INVALID`. Do not use catch-`22023`, because it admits POSIX strings (`UTC+5` means UTC−5), abbreviations and misspellings.
2. Make the match case-sensitive (store the canonical spelling) rather than `lower()`-insensitive. Case-insensitive matching is unambiguous, but it is a nicety nobody asked for.
3. Reject names that collide with an abbreviation (`CET`, `EET`, `MET`, `WET` silently lose DST in `AT TIME ZONE`), optionally together with `Factory` and `posixrules`. Alternatively accept them and document the behaviour. Recommendation: reject them with a `NOT EXISTS (… pg_timezone_abbrevs WHERE lower(abbrev) = lower($tz))` clause, since `Etc/UTC` and `Europe/Paris` remain available.
4. Use one `UPDATE … SET col = COALESCE($x, col) … RETURNING …, today_local` per PATCH. This gives atomicity (RFC 5789), merged values without a read, and `todayLocal` in the new zone from Postgres.
5. Run `validateThresholds` on the merged pair (patch over the guard's values) before SQL. It gives the friendly `422 THRESHOLDS_INVALID` and keeps values above 32767 away from `smallint`.
6. Also map `DrizzleQueryError` with `cause.code === '23514'` and `cause.constraint === 'dealership_thresholds_chk'` to `422 THRESHOLDS_INVALID` with a fixed message. That covers the concurrent-PATCH race, which is otherwise a 500. Never echo `cause.detail`.
7. zod body: `z.strictObject({ timezone: text().optional(), watchDays: z.int().optional(), agingDays: z.int().optional() })`. `null` gives 400. Range and order are left to `validateThresholds` (422).
8. Treat `{}` as a no-op: 200 with the current settings, the same shape as `GET`.
9. The 422s are either `CodedHttpException` without `errors[]` (no shared change), or `CodedHttpException` extended with optional `errors[{pointer}]` passed through `describeException`, a small shared change and a candidate ADR 0007 note. Pick one.
10. `GET` gets `@Header('Cache-Control', 'no-store')`. `PATCH` gets none, matching `PATCH …/status`.
11. Register `DealershipsModule` in both `RouterModule` and `imports`, regenerate `openapi.json`, add the path to `openapi.spec.ts`, add `settings` to the rbac `suffix` list and a `PATCH settings` role test.
