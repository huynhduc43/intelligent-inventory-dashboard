# Vehicle intake building blocks (research for #12)

Research for issue #12 (`POST /api/v1/dealerships/{d}/vehicles`; §4.3, §4.7, D8, D18, D19, ADR 0002, ADR 0013). The route, the permission (`vehicle:create`), the body `{vin, make, model, modelYear, mileage, listPrice?, stockedOn}` and the `409 VIN_ALREADY_IN_STOCK` are taken as given. This note checks how the pieces behave. Four findings shape the design. (1) `INSERT … ON CONFLICT (dealership_id, vin) WHERE status <> 'SOLD' DO NOTHING RETURNING …` infers the partial unique index `vehicle_dealership_vin_open_uq` as its arbiter. A duplicate returns zero rows with no error, and two concurrent inserts of one VIN are race-free at READ COMMITTED: the second waits for the first transaction, then does nothing if it committed or inserts if it rolled back. Leaving out the `WHERE` makes inference fail, and `ON CONSTRAINT <index name>` fails too. (2) The alternative, catching `23505`, works but is indirect. Drizzle 0.45.4 wraps every driver error in `DrizzleQueryError`, and the pg `DatabaseError` with `code` and `constraint` is on `.cause`. (3) `z.iso.date()` in zod 4.6.7 rejects `2025-02-30` and `2023-02-29` but accepts `0000-01-01`, which Postgres rejects with `22008` (a 500). (4) `numeric(12,2)` rounds extra decimals silently (`1.005` → `1.01`) and raises `22003` above 10 integer digits. A decimal string with a strict regex avoids both problems, matches the `listPrice: string` the API already returns, and avoids binary floating point. The VIN check digit (position 9) is required by 49 CFR 565.15 for US-market vehicles only. It is not part of the shared 17-character format, so an API serving several countries should not enforce it.

Method: claims were checked against the PostgreSQL 17 docs, 49 CFR 565 (via the Cornell LII copy; ecfr.gov redirects automated clients to a bot check), RFC 8259, and the installed packages in `node_modules/.pnpm` (`drizzle-orm@0.45.4`, `pg@8.23.1`, `pg-protocol@1.16.1`, `pg-types@2.2.0`, `zod@4.6.7`). The probes were throwaway scripts kept outside the repo (scratchpad). They ran against a separate `postgres:17.11-alpine` container with the committed migrations (`apps/api/db/migrations/0000_init.sql`, `0001_…`) applied, using concurrent `psql` sessions, and against the same container through `drizzle-orm/node-postgres` from `apps/api`. Line numbers refer to the installed package files of the version named. The ISO 3779 text is paywalled (iso.org returned 403) and the EU text could not be fetched (EUR-Lex and legislation.gov.uk returned empty pages to the fetcher), so the claim about Europe in §3 rests on a secondary source and is labelled as such.

## 1. The insert: `ON CONFLICT DO NOTHING` against the partial unique index

The index (`apps/api/src/shared/schema.ts` L115-L117; migration `0000_init.sql` L69):

```sql
CREATE UNIQUE INDEX "vehicle_dealership_vin_open_uq" ON "vehicle" USING btree ("dealership_id","vin") WHERE "vehicle"."status" <> 'SOLD';
```

- **Inference matches it, but only with the predicate.** "All _table_name_ unique indexes that, without regard to order, contain exactly the _conflict_target_-specified columns/expressions are inferred (chosen) as arbiter indexes". `index_predicate` is "Used to allow inference of partial unique indexes. Any indexes that satisfy the predicate (which need not actually be partial indexes) can be inferred" ([INSERT, Parameters → ON CONFLICT Clause](https://www.postgresql.org/docs/17/sql-insert.html#SQL-ON-CONFLICT)). The docs' own example infers a partial index with `ON CONFLICT (did) WHERE is_active DO NOTHING` (same page, Examples). Probe results:

  | Conflict clause                                                         | Result on a duplicate open VIN                                                                                               |
  | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
  | `ON CONFLICT (dealership_id, vin) WHERE status <> 'SOLD' DO NOTHING`    | `INSERT 0 0`, `RETURNING` gives 0 rows. `EXPLAIN` shows `Conflict Arbiter Indexes: vehicle_dealership_vin_open_uq`           |
  | `ON CONFLICT (dealership_id, vin) DO NOTHING` (no predicate)            | `ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification`                                   |
  | `ON CONFLICT ON CONSTRAINT vehicle_dealership_vin_open_uq DO NOTHING`   | `ERROR: constraint "vehicle_dealership_vin_open_uq" for table "vehicle" does not exist` (a unique index is not a constraint) |
  | `ON CONFLICT DO NOTHING` (no target)                                    | `INSERT 0 0`. It works, but it swallows a conflict on _any_ unique index or constraint                                       |
  | `ON CONFLICT (dealership_id, vin) WHERE status = 'IN_STOCK' DO NOTHING` | also inferred, because the predicate implies the index's                                                                     |
  | same VIN after the open row was sold                                    | `INSERT 0 1`: the sold row is outside the partial index, so the car is re-acquired as a new row (D18)                        |

  On the no-target form, the docs say: "when omitted, conflicts with all usable constraints (and unique indexes) are handled" (same page). On naming the arbiter: "It is often preferable to use unique index inference rather than naming a constraint directly", and "only `NOT DEFERRABLE` constraints and unique indexes are supported as arbiters" (same page). The explicit target with the exact predicate is the precise form: it names the one conflict that should become 409.

- **`RETURNING` on conflict yields zero rows.** "Only rows that were successfully inserted or updated will be returned" ([INSERT, Description](https://www.postgresql.org/docs/17/sql-insert.html)). Through drizzle the probe got `rowCount: 0, rows: []` and no exception. The command tag's count is "the number of rows inserted or updated" (same page, Outputs).

- **Zero rows has exactly one cause.** The `DealershipGuard` has already established that the dealership exists and that the user is a member, so the only way the statement inserts nothing is an arbiter conflict. A CHECK, FK or `22xxx` failure still raises an error: `DO NOTHING` covers only arbiter conflicts. So unlike the action insert (ADR 0013), the 0-row path needs no re-read: 0 rows → `409 VIN_ALREADY_IN_STOCK`. A re-read is useful only to put the conflicting vehicle's id in the problem body, and it can race (the open row may be sold in between). Leave it out.

- **Race-free under READ COMMITTED.** The docs: "`INSERT` with an `ON CONFLICT DO NOTHING` clause may have insertion not proceed for a row due to the outcome of another transaction whose effects are not visible to the `INSERT` snapshot. Again, this is only the case in Read Committed mode" ([13.2.1](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)). The waiting comes from the unique check: "If a conflicting row has been inserted by an as-yet-uncommitted transaction, the would-be inserter must wait to see if that transaction commits. If it rolls back then there is no conflict … if a conflicting valid row has been deleted by an as-yet-uncommitted transaction, the would-be inserter must wait for that transaction to commit or abort, and then repeat the test" ([62.5 Index Uniqueness Checks](https://www.postgresql.org/docs/17/index-unique-checks.html)). Probe results (session A holds its change open for 3 s, and session B runs the insert 0.7 s later; `pg_stat_activity` showed B on `Lock / transactionid` while it waited):

  | Session A, uncommitted                               | Then A   | Session B's insert of the same VIN                                                              |
  | ---------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------- |
  | `INSERT … ON CONFLICT … DO NOTHING`                  | commit   | waited 2.27 s, then `INSERT 0 0`, 0 rows returned → 409. One row in the table                   |
  | `INSERT … ON CONFLICT … DO NOTHING`                  | rollback | waited 2.28 s, then `INSERT 0 1` with the row returned → 201. One row in the table              |
  | `INSERT …` (B uses a plain insert, no `ON CONFLICT`) | commit   | waited 2.27 s, then `ERROR 23505 … violates unique constraint "vehicle_dealership_vin_open_uq"` |
  | sells the existing open row (`status = 'SOLD'`)      | commit   | waited 2.28 s, then `INSERT 0 1`: old row `SOLD`, new row `IN_STOCK` (re-acquisition)           |
  | sells the existing open row                          | rollback | waited 2.26 s, then `INSERT 0 0` → 409                                                          |

  In every interleaving there is exactly one open row per VIN and B's answer matches the committed outcome. No lock or transaction is needed: a single autocommit statement, the "conditional SQL, not locks" pattern ADR 0013 uses for actions.

- **Two statements would not be race-free.** A `SELECT … WHERE vin = $1 AND status <> 'SOLD'` followed by an `INSERT` has the gap ADR 0013 rejects for actions: both requests see no open row. The unique index would still stop the second insert, but it would arrive as an unhandled `23505`, a 500.

## 2. The alternative: catch `23505` from drizzle and node-postgres

- **Drizzle wraps every driver error.** `db.execute(sql)` (`drizzle-orm/pg-core/db.js` L273-L288) prepares a query, and `NodePgPreparedQuery.execute` runs `client.query` inside `this.queryWithCache(…)` (`drizzle-orm/node-postgres/session.js` L100-L127). With no cache configured (the app sets none), `queryWithCache` is `try { return await query(); } catch (e) { throw new DrizzleQueryError(queryString, params, e); }` (`drizzle-orm/pg-core/session.js` L36-L42; every other branch L43-L98 wraps the same way). `DrizzleQueryError` extends `Error`, its message is `Failed query: <sql>\nparams: <params>`, and it keeps the driver error as `cause` (`drizzle-orm/errors.js` L10-L21). It is exported from the package root (`drizzle-orm/index.js` L5, `export * from "./errors.js"`).
- **The pg error is on `.cause`.** pg throws `pg-protocol`'s `DatabaseError` (`pg/lib/index.js` L10, L29). The parser copies the server's fields onto it: `code` (SQLSTATE), `detail`, `constraint` (field `n`, `pg-protocol/dist/parser.js` L296-L319), `table`, `schema`. Probe through drizzle, duplicate open VIN with a plain insert: `e instanceof DrizzleQueryError === true`, `e.code === undefined`, `e.cause instanceof pg.DatabaseError === true`, `e.cause.code === '23505'`, `e.cause.constraint === 'vehicle_dealership_vin_open_uq'`, `e.cause.table === 'vehicle'`.
- **So a catch would be:** `e instanceof DrizzleQueryError && e.cause?.code === '23505' && e.cause.constraint === 'vehicle_dealership_vin_open_uq'`. It has to test the constraint name too, or a future unique index would also map to `VIN_ALREADY_IN_STOCK`. Compared with `ON CONFLICT`, it depends on drizzle's internal wrapping (an implementation detail of the installed version), on a constraint name held as a string, and on an exception for an expected outcome. Inside a transaction, a `23505` aborts the transaction while `DO NOTHING` does not. That does not matter for a single autocommit statement, but it would matter if the insert were ever wrapped.
- **Today a raw `DrizzleQueryError` becomes a 500.** `problem-details.filter.ts` treats any non-`HttpException` as `500 INTERNAL` (L13, L26, L46; `problem.ts` L141). This applies to every `22xxx` error listed in §3 and §4 below, so those must be stopped by the schema.

## 3. Request validation with zod 4.6.7

House rules: module-level `z.strictObject` through `@Body({ schema })` and Nest's Standard Schema pipe, with unknown keys rejected (ADR 0005), and every free-text field built on `text()`, which refuses U+0000 because Postgres rejects it in `text` with `22021`, a 500 (`apps/api/src/shared/text.ts`, ADR 0004).

### `stockedOn`: `z.iso.date()`

- **What it checks.** `z.iso.date()` is `core._isoDate(ZodISODate, …)` (`zod/v4/classic/iso.js` L7-L9). The pattern is `dateSource`, anchored (`zod/v4/core/regexes.js` L73, L80). It encodes month lengths and the Gregorian leap rule: `02-29` only for years divisible by 4 and not by 100, or divisible by 400; 30-day months stop at `30`; February otherwise stops at `28`. Output stays a `string`, not a `Date`.
- **Probe results** (`safeParse(...).success`): `2025-02-28` true, `2025-02-30` **false**, `2024-02-29` true, `2023-02-29` false, `1900-02-29` false, `2000-02-29` true, `2025-1-01` false, `2025-01-01T00:00:00Z` false, `" 2025-01-01"` false, full-width digits false, **`0000-01-01` true**.
- **The gap: year 0000.** `\d{4}` admits year `0000`, and Postgres rejects it: `SELECT '0000-01-01'::date` → `22008 date/time field value out of range` (probe, both `psql` and through drizzle). Unless something stops it, that is a 500. A range check closes it, and it is a business rule anyway: `stockedOn` should not be after the dealership's local today (a future stocking date gives a negative age and a tier the policy never defines). `ctx.todayLocal` is already on the request context as a `YYYY-MM-DD` string computed in Postgres (`apps/api/src/modules/auth/dealership.guard.ts` L72, `request-context.ts` L10). Comparing two ISO date strings lexicographically is ordinary string comparison, not time-zone maths, so it stays within the "Node never does time-zone maths" rule. A lower bound (for example `>= '1900-01-01'`) removes year 0000. Alternatively, put the bound into the SQL (`WHERE $stocked_on::date <= $today::date`), which turns the case into a 0-row result that can no longer be told apart from a VIN conflict. Validation in the schema or service is simpler.

### `listPrice` for `numeric(12,2)`: decimal string or JSON number

- **What Postgres does with it.** "if the scale of a value to be stored is greater than the declared scale of the column, the system will round the value to the specified number of fractional digits. Then, if the number of digits to the left of the decimal point exceeds the declared precision minus the declared scale, an error is raised" ([8.1.2 Arbitrary Precision Numbers](https://www.postgresql.org/docs/17/datatype-numeric.html#DATATYPE-NUMERIC-DECIMAL)). Probe: `'1.005'::numeric(12,2)` → `1.01`; `'12345678901.00'::numeric(12,2)` → `22003` (a 500). So the schema must reject a third decimal (otherwise the client's price silently changes) and more than 10 integer digits.
- **Reading back.** `pg-types` registers no parser for `numeric` (OID 1700 is absent from `pg-types/lib/textParsers.js` L167-L196), so it comes back as a string. The probe's `RETURNING list_price` gave `'19999.99'`. The existing read model already exposes it as a string: `listPrice: string | null` (`apps/api/src/modules/inventory/vehicles.service.ts` L15, L35, L74), and the committed `docs/api/openapi.json` documents it as `{"type": "string", "nullable": true, "description": "Decimal string, e.g. \"23995.00\""}`.
- **JSON numbers and floats.** RFC 8259 leaves number precision to implementations and notes that only IEEE 754 binary64 values are interoperable ([RFC 8259 §6](https://www.rfc-editor.org/rfc/rfc8259#section-6)). Most decimal fractions are not exact in binary64 (`0.1 + 0.2 === 0.30000000000000004` in the probe). A two-decimal value below 10^10 still round-trips through `JSON.parse` and `String()` (`19999.99` and `9999999999.99` both did), so plain prices survive. But `z.number().multipleOf(0.01)` decides with a float tolerance (`zod/v4/core/util.js` L58-L66, `floatSafeRemainder`, `4 * Number.EPSILON` relative), not decimal arithmetic. It also accepts `1e2`, and the value would reach SQL as a JS number that pg serialises with `String()`. That probably works, but it rests on reasoning about floats, where the string path rests on a regex.
- **A decimal string** with `z.string().regex(/^(0|[1-9]\d{0,9})(\.\d{1,2})?$/)` (or `\.\d{2}` to require exactly two decimals) is exact by construction. It is bound as text to `::numeric`, so no float is ever involved. It cannot overflow `numeric(12,2)` or be rounded, and negatives are refused before `vehicle_price_chk` (which would otherwise raise `23514`, a 500). It also has the same type as the response, so a client can send back what it read. The cost: clients send `"19999.99"` rather than `19999.99`, and the OpenAPI schema should say so with a `pattern`.
- **Recommendation:** decimal string, nullable and optional (`listPrice?: string | null`, absent or `null` meaning "no price yet", schema.ts L93).

### Other fields

- `vin`: `text().trim().toUpperCase()` then `regex(/^[A-HJ-NPR-Z0-9]{17}$/)`, the same pattern as `vehicle_vin_chk` (`0000_init.sql` L42), so the CHECK never fires from the API. Uppercase before the regex (D18 "uppercased"). Running the regex after the transform also catches Unicode case mappings that change length (`'ß'.toUpperCase() === 'SS'`).
- `make`, `model`: `text().trim().min(1).max(…)`. The columns have no length CHECK, so pick a max for the API.
- `modelYear`: `z.int()` with bounds. The column is `smallint` with no CHECK (`0000_init.sql` L33), so anything above 32767 raises `22003`, a 500. A range such as `1900 … todayLocal year + 1` keeps it meaningful (manufacturers sell next year's models early).
- `mileage`: `z.int().min(0).max(2147483647)` (an `integer` column, `vehicle_mileage_chk >= 0`).

## 4. VIN rules: the character set and the check digit

- **Format (US rule).** "Each VIN shall consist of seventeen (17) characters" (49 CFR 565.13(b)). Characters must come from the letters `ABCDEFGHJKLMNPRSTUVWXYZ` and the numerals `0123456789`, so I, O and Q are excluded (565.13(g)) ([49 CFR 565.13](https://www.law.cornell.edu/cfr/text/49/565.13)). That is exactly the `vehicle_vin_chk` regex.
- **Check digit (US rule).** "The check digit shall appear in position nine (9) of the VIN" (565.13(c)). The algorithm: transliterate letters (Table III), multiply by position weights (Table IV), sum, divide by 11, and the remainder is the digit, with 10 written `X` (Table V) ([49 CFR 565.15(c)](https://www.law.cornell.edu/cfr/text/49/565.15)). Its stated purpose is "to provide a means for verifying the accuracy of any VIN transcription".
- **Scope of that rule.** Part 565 subpart B applies to vehicles made for the US market from the 2009 model year onward (565.2(a)), and it excludes some imported vehicles from 565.13(b), (c), (g) and 565.15 ([49 CFR 565.2](https://www.law.cornell.edu/cfr/text/49/565.2)). It is a US Federal regulation, not a world standard.
- **Outside North America (secondary source).** ISO 3779 defines the 17-character structure (WMI, VDS, VIS). According to the Wikipedia summary, position 9 is "compulsory for vehicles in North America and China, but not so in Europe" ([Vehicle identification number, Components](https://en.wikipedia.org/wiki/Vehicle_identification_number)). In Europe, position 9 is part of the manufacturer's vehicle descriptor section. The ISO text (paywalled) and the EU type-approval text (Regulation (EU) No 19/2011, which could not be fetched) were not read. Treat this point as unverified against the primary source, but note that it is consistent with 565.2: the check digit is a market-specific regulation layered on the ISO structure.
- **What follows for this API.** The design serves dealerships in several countries (each has an IANA time zone, §4.3). A European-market VIN with a non-checksum position 9 is valid and would be wrongly rejected by a mandatory check. Grey imports and pre-1981 vehicles are other cases; the latter fail the 17-character rule anyway. The seed's VINs (`'SEED' || dch || lpad(n, 12, '0')`, `apps/api/db/seed.ts` L77) do not carry valid check digits either. That matters only if a check were added to the database. D18 already fixes the format check (17 characters, the set above, uppercased) and says nothing about a checksum.
- **Options:** A. Format only (D18, matches the CHECK). B. Format, plus the check digit for every VIN. C. Format, plus the check digit only for some markets (for example a per-dealership flag, or VINs whose WMI starts with `1`–`5`, North America). Recommendation: **A**. B rejects valid non-US VINs. C needs a market attribute the data model does not have, and it is a feature nobody has asked for. If a typo guard is wanted later, a non-blocking warning is the safer form.

## 5. House conventions that bear on the design

- **Raw SQL through `db.execute(sql\`…\`)`**, with explicit casts and snake_case rows mapped in the service, as in `vehicles.service.ts`(L129-L150) and`actions.service.ts`(L56-L61). Return`stocked_on::text`, as the read model does (`vehicles.service.ts`L59), so the date comes back as`YYYY-MM-DD`and not as a JS`Date`.
- **Conditional single-statement writes** decide the outcome inside one SQL statement, with no transaction or lock, and branch on the row count ([ADR 0013](../adr/0013-actions-read-vehicle-status-in-the-insert.md); CLAUDE.md, "Race-free writes via conditional SQL, not locks"). `INSERT … ON CONFLICT … DO NOTHING RETURNING` is the intake form of that pattern.
- **`updated_at` from the injected `Clock`** ([ADR 0002](../adr/0002-updated-at-set-from-clock.md)). The column defaults to `now()` "for inserts only", so the default is allowed. But passing `${this.clock.now().toISOString()}::timestamptz` for `updated_at` (and `created_at`) keeps tests pinnable and matches what `actions.service.ts` L58 does for `created_at`. `updated_by` = the authenticated user (D19).
- **`text()` for free-text fields** (`apps/api/src/shared/text.ts`; issue #51): `vin`, `make` and `model` must be built on it.
- **D8** (`docs/research/backend-architecture.md` §2): data comes from the seed plus `POST /vehicles` and a status-change endpoint. CSV import is deferred (§6.2), and §6.2 names "the unique `(dealership_id, vin)` index" as its future upsert target, which is the same arbiter as this insert.
- **D18**: 17 characters, `[A-HJ-NPR-Z0-9]`, uppercased, immutable, unique among non-sold vehicles per dealership, and a re-acquired car gets a new row. The test plan (§4.15) asks for format, uppercasing, uniqueness among non-sold vehicles and re-acquisition, in unit and integration tests. §4.12 places a `domain/vin.ts` in `inventory`.
- **D19**: `vehicle.updated_by` and `updated_at` are the audit trail.
- **§4.3**: the column types quoted above, `list_price` nullable, `status` defaults to `IN_STOCK`, `sold_at` NULL (`vehicle_sold_at_chk`). Intake never sets `status` or `sold_at`.
- **§4.7**: `201` with `Location` and the vehicle as the body; errors are `400, 404, 409 VIN_ALREADY_IN_STOCK`. For `Location`, `vehicle-actions.md` §1 and §5 already settled the mechanics: RFC 9110 §10.2.2, Nest's POST default of 201, and `@Res({ passthrough: true })` with `res.location(…)`. Here the target `GET /dealerships/{d}/vehicles/{v}` exists, so `Location: /dealerships/{d}/vehicles/{id}` resolves. The body should be the same shape as that `GET` (with `daysInStock`, `tier`, `currentAction: null`), which favours re-using the detail read after the insert, or computing those fields in the `RETURNING`.

## Decisions this suggests

1. Write with one statement, `INSERT … ON CONFLICT (dealership_id, vin) WHERE status <> 'SOLD' DO NOTHING RETURNING …`, with the predicate written exactly as the index has it; never `ON CONSTRAINT`, never a target-less `DO NOTHING`.
2. 0 rows → `409 VIN_ALREADY_IN_STOCK` directly, with no re-read (the guard has already proved the dealership exists, so a conflict is the only cause).
3. Do not catch `23505`; leave any other DB error to the filter as a 500, and stop every known `22xxx` case in the schema.
4. `stockedOn`: `z.iso.date()` plus a range check (not before 1900-01-01, not after `ctx.todayLocal`, compared as strings), so year 0000 and future dates are 400s, not a 500 and negative ages.
5. `listPrice`: optional, nullable decimal string matching `^(0|[1-9]\d{0,9})(\.\d{1,2})?$`, bound as `::numeric`; never a JSON number (no float, no silent rounding, same type as the response).
6. `vin`: `text().trim().toUpperCase()` and then the `vehicle_vin_chk` regex; no check-digit validation (US-only rule; it would reject valid non-US VINs).
7. Bound `modelYear` (smallint) and `mileage` (integer, ≥ 0), and build `make`/`model` on `text().trim().min(1).max(n)`, so no input reaches a `22003`/`22021`/`23514`.
8. Set `updated_at` and `created_at` from `Clock.now()` and `updated_by` from the user; never set `status` or `sold_at` on intake.
9. Respond `201` with `Location: /dealerships/{d}/vehicles/{id}` and a body shaped like the vehicle detail response.
10. Integration tests: duplicate open VIN → 409; same VIN after sale → 201 (re-acquisition); two concurrent inserts of one VIN → exactly one 201 and one 409, with one open row.
