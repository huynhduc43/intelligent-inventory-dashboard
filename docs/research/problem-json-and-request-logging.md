# Problem+json errors and request-scoped logging (research for #7)

Research for issue #7 (§4.7, §4.8, §5.1, ADR 0003). The current packages fit together: `nestjs-pino@5.3.1` + `pino-http@11.0.0` + `pino@10.4.0` support NestJS 12 and ESM, and Nest 12.3.2 sends unknown routes, malformed JSON, oversized bodies and handler errors to one global filter (`APP_FILTER` or `useGlobalFilters`). Five findings shape the design. (1) Nest registers the body parser **before** any Nest middleware, so on a malformed or oversized body the `nestjs-pino` middleware never runs: no `req.id`, no `X-Request-ID` and no request log line, unless something changes the order. (2) `pino-http` puts the real error and its stack on the completion line only if `res.err` is set before the response finishes. Otherwise a 5xx carries a made-up `Error('failed with status code 500')`. (3) Terminus throws `ServiceUnavailableException(result)`, which a catch-all filter would rewrite; Terminus has no option to prevent this. (4) Nest 12 ships `StandardSchemaValidationPipe`, which accepts zod 4 schemas with no new dependency. (5) RFC 9457's own `errors` example uses `detail` and `"#/age"`, not `message` and `"/age"` as §4.8 does, and `urn:request:` uses an unregistered URN namespace.

Method: the claims below were checked against the published package tarballs (`npm pack`), the installed `@nestjs/*@12.3.2` and `@nestjs/terminus@12.1.0` builds, the NestJS docs sources, the RFC texts, and a throwaway Nest 12.3.2 + Express 5 probe kept outside the repo. Line numbers refer to the published package files of the version named.

## 1. nestjs-pino, pino-http, pino: versions and wiring

| Package       | Latest (npm, 2026-11-02) | Relevant peers / notes                                                                                                             |
| ------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `nestjs-pino` | 5.3.1                    | peers `@nestjs/common` and `@nestjs/core` `^11.0.8 \|\| ^12.0.2`, `pino ^10`, `pino-http ^11`, `rxjs ^7.1`; `engines.node >=22.12` |
| `pino-http`   | 11.0.0                   | depends on `pino ^10`; CommonJS with `module.exports.default` and a named `pinoHttp` export                                        |
| `pino`        | 10.4.0                   | CommonJS (`"type": "commonjs"`); redaction now comes from `@pinojs/redact`, although `docs/redaction.md` still names `fast-redact` |

- **NestJS 12.** The peer floor is `12.0.2`. `apps/api/package.json` asks for `^12.0.1`, but the lockfile resolves 12.3.2, which satisfies it. Raising the floor would make the requirement explicit (README §Migration v5).
- **ESM.** `nestjs-pino` 5 publishes an `exports` map with an `import` condition pointing at `dist/esm/index.js` (`npm view nestjs-pino exports`), so the app imports it with `import { LoggerModule, Logger } from 'nestjs-pino'`. Deep imports no longer resolve (README §Migration v5). `pino` and `pino-http` are CommonJS; Node's ESM loader imports them by default import.
- **Register once.** `LoggerModule` is `@Global()`. Registering it twice (for example, a bare `LoggerModule` import in a feature module) mounts the middleware twice and logs every request twice, with no warning (README lines 130–140).
- **Config.** `forRootAsync({ imports, inject, useFactory, providers })` builds the `PARAMS_PROVIDER_TOKEN` provider from the factory (`dist/esm/LoggerModule.js`; README §Asynchronous configuration). `SharedModule` is `@Global()` and exports `APP_CONFIG`, so `inject: [APP_CONFIG]` works without `imports`. `AppModule.forRoot(config)` already holds the parsed config, so plain `LoggerModule.forRoot({ pinoHttp: { level: config.LOG_LEVEL, … } })` works as well. The two are equivalent; the second skips DI.
- **`bufferLogs` + `useLogger`.** Call `NestFactory.create(AppModule, { bufferLogs: true })`, then `app.useLogger(app.get(Logger))` **before** `init()` or `listen()`. Since Nest 12.1.1, `init()` flushes the buffer, so a logger set after `init()` misses the startup logs (README lines 77–78 and 993). `main.ts` currently calls `listen()` directly, so it would only need the two lines.
- **Middleware scope.** The middleware is applied in `configure()` to `{ path: '{/*splat}', method: ALL }` (`LoggerModule.js`, `DEFAULT_ROUTES`), so it also runs for unknown routes; the probe saw a Nest middleware run before the 404 handler. Nest registers middleware from global modules first (`@nestjs/core` `middleware/middleware-module.js:81-96`), so `pino-http` runs before any non-global module's middleware.
- **Request ID.** `pino-http` does `req.id = req.id || genReqId(req, res)` (`logger.js:141`); an ID something earlier put on `req.id` is kept. The README example reuses `req.headers['x-request-id']` and only sets the response header when it generates an ID (README lines 149–155). To echo the ID on **every** response, the header has to be set whether the ID was reused or generated. The nestjs-pino FAQ points to `genReqId` for this (README line 1048).
- **Redaction.** Use pino's `redact` option (`docs/redaction.md`): paths use ECMAScript lookup syntax, are case-sensitive, and `*` stands for one level. Node lower-cases request header names, so the request serializer's output is redacted with `req.headers.authorization`. `*.password` matches `password` exactly one level down (`body.password`, `user.password`); it does not match a top-level `password` or deeper nesting. Request bodies are not logged by default (pino-http README line 425).
- **`customProps`.** It is evaluated twice: when the middleware runs (`logger.js:146-148`) and again when the response finishes (`logger.js:105-111`). The second run creates a child logger only if the stringified result is not already in the bindings. So `user_id` and `dealership_id`, which a guard sets on `req` after the middleware, still reach the completion line. A key with a defined value at both times but a different value would appear twice in the JSON. The alternative, `PinoLogger.assign`, reaches the completion line only with `assignResponse: true` (`params.d.ts`; README §Assign extra fields).
- **§5.1 field names.** By default pino-http logs `req` and `res` objects and `responseTime` (pino-http README line 109). `customAttributeKeys` renames `req`, `res`, `err` and `responseTime`, and renames `reqId` only with `quietReqLogger`. Flat fields (`req_id`, `method`, `route`, `status`, `duration_ms`) need `customSuccessObject`/`customErrorObject` or custom serializers; `formatters.level` and `timestamp` control `level` and `time` (pino `docs/api.md` §formatters). `req.route?.path` holds the matched Express route (the probe saw `/boom`); it is `undefined` for 404s and body-parser errors.
- **Quiet tests.** The validated `LOG_LEVEL` enum already includes `silent`. pino drops everything at that level, and pino-http returns early on `silent` (`logger.js:101`). For tests that assert on log lines, `pinoHttp` also accepts `[options, destinationStream]` (`params.d.ts`), which lets a test capture lines in memory.
- **Shutdown.** `main.ts` calls `enableShutdownHooks()`. Logs written in shutdown hooks are lost only with an asynchronous destination or a transport; in that case use `enableShutdownHooks(undefined, { useProcessExit: true })` (README §Flushing on shutdown).

### Gap: errors raised before the logging middleware runs

Nest's `init()` calls `registerParserMiddleware()` before `registerModules()` and `registerRouter()` (`@nestjs/core` `nest-application.js:123-131`), so `express.json()` runs before every `MiddlewareConsumer` middleware, `nestjs-pino`'s included. When body-parser calls `next(err)`, Express skips straight to the error handler. In the probe, a malformed body and a 413 reached the global filter with **no `req.id`** and without the Nest middleware having run. A middleware mounted with `app.use()` in `main.ts` before `listen()` **did** run before the parser and its `req.id` reached the filter. The options are listed under Decisions (Q2).

## 2. The global filter, `req.id`, and 5xx stacks on the completion line

- **`APP_FILTER` vs `useGlobalFilters`.** Both end up in `config.getGlobalFilters()`. With the static scope they apply to route handlers, to the 404 handler and to the Express error layer, which handles body-parser errors (`router/router-exception-filters.js:29-42`, `router/routes-resolver.js:77-104`); the probe caught 404, malformed JSON and 413 with an `APP_FILTER`. Only `APP_FILTER` supports dependency injection (for `APP_CONFIG` or `HttpAdapterHost`); `useGlobalFilters()` instances are created outside any module (Nest docs, [exception-filters §Binding filters](https://docs.nestjs.com/exception-filters#binding-filters), source lines 351–369). A request- or transient-scoped `APP_FILTER` is **not** applied outside controllers, and Nest logs a warning about it (`router-exception-filters.js:48-55`). Exceptions thrown in middleware reach only global filters (docs line 371).
- **Reading the ID.** `host.switchToHttp().getRequest().id` is whatever pino-http set. pino-http's typings declare `IncomingMessage.id: ReqId` (`number | string | object`) as non-optional (`index.d.ts:80-89`), but at runtime it is `undefined` on the pre-middleware paths in §1.
- **What pino-http does on its own.** It only listens for `finish`, `close` and `error` on the response (`logger.js:198-202`); it has no knowledge of Nest filters. When the response finishes it logs one line. If `res.err` is set, or the status is ≥ 500, it logs the error object under `err` with the message `request errored`. When `res.err` is not set, that object is `new Error('failed with status code ' + res.statusCode)`, whose stack points into pino-http (`logger.js:114-126`). It logs at `useLevel` (default `info`) unless `customLogLevel(req, res, err)` returns another level (README line 99). nestjs-pino adds nothing for HTTP errors beyond `LoggerErrorInterceptor`.
- **`LoggerErrorInterceptor`** sets `response.err = error` in `catchError` before rethrowing (`dist/esm/LoggerErrorInterceptor.js`; README §Expose stack trace). It sees only errors raised inside the interceptor chain. Pipes run inside it, but guards run before interceptors (`router/router-execution-context.js:46-49, 66-88`). Middleware, 404 and body-parser errors never reach it. It also sets `res.err` for 4xx `HttpException`s, which turns those lines into `request errored` lines with a stack.
- **Setting `res.err` in the filter** (for example, only for 5xx) covers every path on which pino-http is attached, because the filter runs before the response is written and pino-http reads `res.err` at `finish`. This is the code path `LoggerErrorInterceptor` relies on.
- **No second error line.** Nest's `BaseExceptionFilter.handleUnknownError` logs every non-`HttpException` through `Logger('ExceptionsHandler')` (`exceptions/base-exception-filter.js:38-58`). A custom filter that does not call `super.catch()` avoids that separate line.

## 3. What Nest 12 + Express 5 throw, and validation-error shapes

Observed in the probe (Nest 12.3.2, Express 5.3.0) and traced to the source:

| Case                         | What reaches the filter                                                                                                                | Source                                                                                     |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Unknown route                | `NotFoundException`, response `{ message: 'Cannot GET /nope', error: 'Not Found', statusCode: 404 }`                                   | `routes-resolver.js:77-83`                                                                 |
| Malformed JSON               | `BadRequestException(syntaxError.message)` (for example `Unexpected end of JSON input`, V8 wording), **no `cause`**, `req.id` unset    | body-parser `lib/read.js:196-198`; `@nestjs/platform-express` `express-adapter.js:494-500` |
| Body > limit (default 100kb) | `HttpException('request entity too large', 413, { cause: PayloadTooLargeError })`; `cause.type === 'entity.too.large'`; `req.id` unset | `express-adapter.js:507-513`; body-parser README §request entity too large                 |
| Bad charset/encoding         | `HttpException` 415 with an http-errors `cause` (same mapping)                                                                         | body-parser `lib/read.js:79-110`                                                           |
| Bad `%` encoding in a path   | `BadRequestException` (from `URIError`)                                                                                                | `express-adapter.js:497-500`                                                               |
| Handler `throw new Error()`  | the raw `Error` (not an `HttpException`)                                                                                               | probe                                                                                      |

body-parser wraps the `SyntaxError` with `createError(400, err, { type: 'entity.parse.failed' })`. The result stays a `SyntaxError`, so `mapException` turns it into a plain `BadRequestException` and the `entity.parse.failed` type is lost. Without the adapter mapping, `BaseExceptionFilter.isHttpError` would recognise an http-errors object by its `expose`/`statusCode`/`status` fields and reply with its status (`base-exception-filter.js:66-93`; Nest docs exception-filters line 18).

Validation options for an RFC 9457 `errors[{ pointer, … }]` list (no decision here):

- **A. `ValidationPipe` + class-validator/class-transformer.** Neither package is installed, so this means two new dependencies. The default body is `{ statusCode: 400, error: 'Bad Request', message: string[] }` (Nest docs [validation](https://docs.nestjs.com/techniques/validation), source lines 186–192). `whitelist` + `forbidNonWhitelisted` rejects unknown properties (lines 231–243). `exceptionFactory(errors: ValidationError[])` would have to walk nested `children` to build pointers. Trade-off: decorator DTOs, a second validation library next to zod (which validates config).
- **B. Nest 12's built-in `StandardSchemaValidationPipe`** (in `@nestjs/common` since at least 12.0.1). It accepts any Standard Schema, zod 4 included, through `@Body({ schema })`, `@Query({ schema })` and `@Param({ schema })`, and leaves parameters without a schema untouched (docs lines 404–470). The default error is `400` with messages like `email: Invalid email address` (`pipes/standard-schema-validation.pipe.js:30-50`). `exceptionFactory(issues)` receives the issues; zod passes its own issue objects through, so `code`, and `keys` on `unrecognized_keys`, are still there at runtime but typed only as `{ message, path }`. Unknown keys are rejected by `z.strictObject()` (docs lines 516–517). Trade-off: no new dependency, idiomatic Nest 12, a schema per parameter.
- **C. A small hand-written zod pipe** (`schema.safeParse` → our exception). Full zod typing and control, but roughly 20 lines the framework already provides in B.

Building pointers, whichever option is chosen (zod 4.6.7, checked):

- An issue's `path` is an array of keys and indexes relative to the validated value. For a body schema, `["a", "x/y~z"]` becomes `/a/x~1y~0z`: escape `~` as `~0` **before** escaping `/` as `~1` (RFC 6901 §3; §4 decodes in the reverse order). A root-level issue has `path: []`, which is pointer `""`.
- `unrecognized_keys` sets `path` to the **parent** and lists the offenders in `keys` (`{"code":"unrecognized_keys","keys":["extra"],"path":[]}`). One pointer per key needs `path.concat(key)`.
- For `@Query` and `@Param`, a JSON Pointer "within the request's content" (RFC 9457 §3) does not strictly apply. Options: point into the query object anyway, or use a different member (for example, a `parameter` name).
- RFC 6901 §6: the URI-fragment form (`#/age`, which RFC 9457 uses) percent-encodes characters not allowed in a fragment; the plain form (`/age`, which §4.8 uses) does not.

## 4. Terminus 12 on a failed check

- `HealthCheckService.check()` returns the result for `ok`/`degraded`. For `error` it logs `Health Check has failed!` through its logger and throws `new ServiceUnavailableException(result)`; for `shutting_down` it throws the same without logging (`@nestjs/terminus@12.1.0` `dist/health-check/health-check.service.js:47-64`). `getResponse()` therefore returns `{ status, info, error, details }`. A catch-all problem+json filter would rewrite it, which ADR 0003 rules out.
- An indicator that **throws** (instead of returning `down()`) aborts the check with a **500** (Nest docs [terminus](https://docs.nestjs.com/recipes/terminus), source line 673). `DatabaseHealthIndicator` catches its error and returns `down()`, so it gives a 503.
- `@HealthCheck()` adds only `Cache-Control: no-cache, no-store, must-revalidate`, plus Swagger metadata when `@nestjs/swagger` is installed (`health-check.decorator.js:13-37`). It sets no metadata that a filter could detect.
- The Terminus options are `errorLogStyle` (`'json' | 'pretty'`, formatting of the log only), `logger` (a class, or `false` to silence it) and `gracefulShutdownTimeoutMs` (`terminus-options.interface.d.ts`). **None of them changes the throw.**
- Filter precedence: the exception handler gets `[...global, ...class, ...method]` reversed and calls the first filter whose `@Catch` matches (`helpers/context-creator.js:4-14`, `exceptions/exceptions-handler.js:19-35`). A controller-scoped filter therefore wins over a global one.

Ways to leave health bodies alone:

| Option                                                                                                                                     | Trade-off                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `@UseFilters(TerminusPassthroughFilter)` on `HealthController`, `@Catch(ServiceUnavailableException)`, replying with `getResponse()` as-is | Keeps ADR 0003 inside the health module; the global filter stays generic. One more small class.                        |
| Global filter passes through `HttpException`s whose response matches Terminus's shape (`status` in `error`/`shutting_down` plus `details`) | No change to the health module; duck typing could catch a future exception of the same shape.                          |
| Global filter passes through by route (`req.route?.path` or the URL starting `/health`)                                                    | Simple; couples the filter to a path string. `ArgumentsHost` has no `getClass()`, so the controller cannot be checked. |
| `HealthController` catches the exception and returns the body with `@Res({ passthrough: true })` and `res.status(503)`                     | No filter involvement; departs from Terminus's documented pattern and duplicates its contract.                         |

Logging side effect: every failed readiness probe produces a pino-http `request errored` line at `error` level (5xx, §2) as well as Terminus's own `Health Check has failed!` line. `autoLogging.ignore` or `customLogLevel` can lower this if probes are frequent.

## 5. RFC 9457, `instance` and the `X-Request-ID` rule

From [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html):

- **No member is required.** "Problem detail objects can have the following members", and a member of the wrong type MUST be ignored (§3.1).
- **`type`** is a URI reference; when absent it means `about:blank` (§3.1.1). It **may be non-resolvable** (a `tag:` URI is the example). If it is an `http(s)` locator, dereferencing it SHOULD give human-readable documentation, and resolvable URIs are encouraged (§3.1.1, §4). Absolute URIs are RECOMMENDED. A new problem type MUST document a type URI, a title and a status code (§4).
- **`title`** is a short summary of the problem **type**. It SHOULD NOT change between occurrences except for localisation (§3.1.3). With `about:blank` it SHOULD equal the status phrase, for example `Not Found` (§4.2.1). Node's `http.STATUS_CODES` still uses older phrases (`413 Payload Too Large`, `422 Unprocessable Entity`) where RFC 9110 uses `Content Too Large` (§15.5.14) and `Unprocessable Content` (§15.5.21).
- **`status`** is advisory. Generators MUST use the same code in the actual response (§3.1.2).
- **`detail`** should help the client fix the problem, not debug the server. Clients SHOULD NOT parse it (§3.1.4). §5 warns against exposing implementation details such as stack dumps.
- **`instance`** is a URI reference for this occurrence; if it cannot be dereferenced it is an opaque identifier (§3.1.5). Absolute URIs are RECOMMENDED; relative ones should carry a full path (`/instances/123`).
- **Extension members** are allowed; clients MUST ignore unknown ones (§3.2). Names SHOULD start with a letter, use only `ALPHA`, `DIGIT` and `_`, and be at least three characters long (§4). `code` and `errors` comply.
- **The `errors` example (§3)** is a 422 whose items are `{ "detail": "...", "pointer": "#/age" }`. The member names are `detail` and `pointer`, and the pointer is in **URI-fragment form**. §4.8 uses `{ pointer: "/status", message }`. The RFC calls its `errors` type fictional, so neither form is mandated.
- **Media type** `application/problem+json`: no required or optional parameters (RFC 7807 §6.1, which RFC 9457 §6 updates). Express's `res.send` appends `; charset=utf-8` to a preset string `Content-Type` (`express@5.3.0` `lib/response.js:140-141`); per RFC 8259 §11 a `charset` parameter has no effect on compliant recipients. Nest's `reply()` keeps a preset `+json` content type (`express-adapter.js:15-18, 143-155`).
- **`Content-Language: en`** appears in the RFC's examples but is not required (RFC 9110 §8.5).

**`urn:request:<id>`.** It is syntactically a URI (`"urn" ":" NID ":" NSS`, where NSS = `pchar *(pchar / "/")`; RFC 8141 §2). However, RFC 8141 §1 says syntactic correctness is not enough for a valid URN: the NID must be registered, and `request` is not in the [IANA URN namespace registry](https://www.iana.org/assignments/urn-namespaces/urn-namespaces.xhtml) (`uuid` is, per RFC 9562; `example` is, per RFC 6963). Because RFC 9457 accepts any URI reference and an opaque one is allowed, `urn:request:` would work in practice but is not a valid URN. Alternatives: `urn:uuid:<id>` (valid only if every ID is a UUID; RFC 9562 §4, Figure 4), or a relative reference such as `/requests/<id>`. Characters allowed without escaping in the NSS are `pchar` (`A–Z a–z 0–9 - . _ ~ ! $ & ' ( ) * + , ; = : @`) plus `/` (RFC 3986 Appendix A). An incoming ID with any other character would need percent-encoding before it can go into `instance`.

**Validating an incoming `X-Request-ID`.** First-party precedents:

- Heroku router: the value "must be between 20 and 200 characters, and consist of ASCII letters, digits, or the characters `+`, `/`, `=`, and `-`. Invalid IDs will be ignored and replaced with generated ones" ([Heroku Dev Center, HTTP Request IDs](https://devcenter.heroku.com/articles/http-request-id)).
- Envoy: generates a UUID when the header is missing. At the edge it **replaces** an incoming ID unless `preserve_external_request_id` is set; its docs describe no validation of the value ([Envoy, x-request-id](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_conn_man/headers#x-request-id)).
- Node joins duplicate unknown headers with `", "` (`X-Request-ID: a` and `X-Request-ID: b` arrive as `"a, b"`; checked on Node 23). A charset without spaces and commas rejects duplicated headers automatically.

Candidate rules (choice open; see Q5): Heroku's `^[A-Za-z0-9+/=-]{20,200}$`; a URN-safe `^[A-Za-z0-9._-]{1,128}$`; or UUID only. On mismatch the precedent is to **ignore and generate a new ID**, not to reject with 400.

## 6. Headers already sent (Express 5 / Nest 12)

- Nest's own filter checks first: `if (!isHeadersSent(res)) reply(...) else end(res)` (`base-exception-filter.js:31-36, 49-54`; `isHeadersSent` is `res.headersSent`, `express-adapter.js:216-218`). The `CatchEverythingFilter` example in the docs does **not** check (exception-filters lines 380–415).
- Probe: a handler that wrote part of a body with `@Res()` and then threw reached the filter with `headersSent: true`. A filter that ignores this throws `ERR_HTTP_HEADERS_SENT` from inside the filter, and the response is never finished by the filter.
- Express 5's final handler, in the same situation, destroys the socket rather than writing (`finalhandler@2.1.1` `index.js:118-123`). The choice is between `res.end()` (Nest's behaviour, which can make a truncated body look complete) and `req.socket.destroy()` (signals the failure to the client).
- In this API it is rare: no streaming or `@Res()` handlers are planned. Still, the check is cheap and the probe shows the failure mode.

## Decisions this informs

1. **Q1, global filter registration.** A: `APP_FILTER` in a module (DI for `APP_CONFIG`/`HttpAdapterHost`, also covers 404 and body-parser errors). B: `useGlobalFilters(new Filter(httpAdapter))` in `main.ts` (no DI, must be repeated in every test bootstrap).
2. **Q2, request ID and log line for pre-middleware errors (malformed JSON, 413, 415).** A: accept the gap; the filter generates an ID itself when `req.id` is missing, sets `X-Request-ID`, and these requests get no pino-http line (or a filter-written line). B: a small `app.use()` request-ID middleware in `main.ts` that sets `req.id` and the header before the body parser; pino-http keeps it. The ID is then consistent, but these requests still get no completion line. C: `NestFactory.create(..., { bodyParser: false })` and mount the JSON parser as module middleware after the global `LoggerModule`. One ID and one line for everything, but it needs `express` (or `body-parser`) as a direct dependency (ask first) and is an unusual setup (Nest docs middlewares line 127). D: mount `pino-http` itself with `app.use()` and set nestjs-pino's `useExisting`. One line for everything, but the logger has to be configured outside Nest DI.
3. **Q3, 5xx stack on the completion line.** A: the filter sets `res.err = exception` for 5xx only (covers guards and middleware). B: `LoggerErrorInterceptor` (handler and pipe errors only, and it also flags 4xx). C: the filter writes its own error line (two lines per failed request, against §5.1). The level mapping (4xx `warn`/`info`, 5xx `error`) is a separate `customLogLevel` choice.
4. **Q4, `instance` format.** A: `urn:request:<id>` as in §4.8 (opaque, readable, unregistered NID). B: `urn:uuid:<id>` (registered, forces UUID-only IDs). C: relative `/requests/<id>` (valid URI reference, implies a resource that does not exist).
5. **Q5, incoming `X-Request-ID` rule.** A: Heroku's 20–200 `[A-Za-z0-9+/=-]` (interoperable with Heroku-style IDs, allows `/` and `+`). B: `[A-Za-z0-9._-]{1,128}` (URN-safe without escaping, rejects joined duplicates). C: UUID only. In every case a bad value is ignored and replaced by a `randomUUID()`, as Heroku does, rather than answered with 400.
6. **Q6, validation mechanism.** A: `ValidationPipe` + class-validator (two new dependencies). B: Nest's `StandardSchemaValidationPipe` with zod 4 and an `exceptionFactory` that builds pointers. C: our own zod pipe.
7. **Q7, `errors[]` item shape.** A: keep §4.8's `{ pointer: "/status", message }`. B: follow the RFC example, `{ pointer: "#/status", detail }`. A third option is plain pointers with `detail`. Also decide how query and path parameters are pointed at.
8. **Q8, `type` and `title`.** A: `about:blank` with the status phrase as `title` for generic errors (404, 500) and minted URIs only for coded problems. B: a minted `type` URI per `code`, even if it does not resolve yet (the RFC says SHOULD resolve; changing the URI later breaks clients). Also decide whether titles use RFC 9110 phrases or Node's `STATUS_CODES`.
9. **Q9, health passthrough (ADR 0003).** A: a controller-scoped filter on `HealthController`. B: the global filter recognises Terminus's shape. C: the global filter recognises the route. D: the controller catches the exception itself. Separately, decide whether probe traffic is excluded from auto-logging or logged at a lower level.
10. **Q10, malformed-JSON `detail`.** A: pass V8's parser message through (useful, but its wording varies with the Node version). B: a fixed message such as "Request body is not valid JSON". The `BadRequestException` carries no `cause`, so the filter can recognise it only as a bare `BadRequestException` with a string message.
