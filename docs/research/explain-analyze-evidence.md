# `EXPLAIN ANALYZE` evidence for the list and dashboard queries (research for #15)

Research for the README's performance section: §1.4 sets "`GET …/dashboard` and a 50-row list page at 2,000 in-stock vehicles: p95 ≤ 300 ms (verified with `EXPLAIN ANALYZE` on a 20k-vehicle seed in the README)" (`docs/research/backend-architecture.md:83`), and §4.14 names `SEED_VEHICLES_PER_DEALERSHIP=20000` (`backend-architecture.md:522`). Four findings shape the work. (1) node-postgres sends every parameterized query as an **unnamed** prepared statement over the extended protocol, and Postgres plans an unnamed statement at Bind time with the actual values, so `EXPLAIN (ANALYZE, BUFFERS)` sent with the **same text and the same params** through `pg` gets the plan the app gets; no literal substitution by hand is needed. (2) drizzle's public `logger` option hands out the exact SQL text and params of every statement, so a small script can call the real service methods and re-send what they ran. (3) At 20,000 per dealership the seed takes about 4 s and creates actions proportionally, but **only on an empty database**: re-seeding on top of the default 250 adds the vehicles and almost no actions. (4) Measured on Postgres 17.11, every statement runs in 1–45 ms at 16,020 in-stock vehicles per dealership (8× the design's 2,000), far inside 300 ms.

Method: PostgreSQL 17 docs (the version in `docker-compose.yml:4`, `postgres:17.11-alpine`); `pg@8.23.1`, `pg-protocol@1.16.1` and `drizzle-orm@0.45.4` source under `node_modules/.pnpm/` (paths below are relative to each package); the repo files named below. A throwaway run on 2026-11-03: `postgres:17.11-alpine` started with `docker run --rm -p 55440:5432` (the compose file hard-codes `5432:5432`, `docker-compose.yml:9`, so `-p iid15research` alone would still have collided with another session's stack on 5432), `db/migrate.ts`, `db/seed.ts` with `SEED_VEHICLES_PER_DEALERSHIP=20000` under Node 24.15, then a scratchpad probe that imported the built `VehiclesService` and `DashboardService` from `apps/api/dist`, captured their SQL through a drizzle logger and re-sent each `SELECT` as `EXPLAIN (ANALYZE, BUFFERS)` with the same params. Container stopped and removed afterwards; nothing committed. `auto_explain` and `log_statement` were **not** run (docs only).

## 1. What the app sends, and whether `EXPLAIN` sees the same plan

- **drizzle → pg.** `db.execute(sql…)` turns the template into `{ sql, params }` with `dialect.sqlToQuery` (`pg-core/db.js:273-276`, `pg-core/dialect.js:428-436`) and runs `client.query({ name, text, types }, params)` (`node-postgres/session.js:21-24,103,113`). `name` is `undefined` on this path (`pg-core/db.js:277-281` passes `void 0`), so the statement is unnamed. The same call passes the text and params to `logger.logQuery(text, params)` first (`node-postgres/session.js:103`; logger option wired in `node-postgres/driver.js:31-36`).
- **pg → protocol.** A query with values "requires preparation" (`pg/lib/query.js:35-58`, "prepare if there are values"), so `pg` sends Parse/Bind/Describe/Execute/Sync with an empty statement name and an empty portal (`query.js:211-249`, `query.js:22`). drizzle's `types` is an object with `getTypeParser`, not an OID array, so Parse carries zero parameter types (`pg-protocol/dist/serializer.js:51-56`: `types.length` is undefined, no OIDs written). Values go as text: arrays become `{"IN_STOCK"}` literals, numbers `toString()` (`pg/lib/utils.js:23-45,51-80`).
- **Postgres.** "Parameter data types can be specified by OID; if not given, the parser attempts to infer the data types in the same way as it would do for untyped literal string constants." "Query planning typically occurs when the Bind message is processed." An unnamed statement "lasts only until the next Parse statement specifying the unnamed statement" ([protocol flow, 53.2.3](https://www.postgresql.org/docs/17/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY)). A plan is reused only for a statement "executed repeatedly", which an unnamed statement re-parsed every call is not. So the app always gets a **custom plan** built with its actual values.
- **Generic vs custom.** "The first five executions are done with custom plans … If a generic plan is in use, it will contain parameter symbols `$n`, while a custom plan will have the supplied parameter values substituted into it" ([PREPARE, Notes](https://www.postgresql.org/docs/17/sql-prepare.html)). `plan_cache_mode` defaults to `auto` and "is considered when a cached plan is to be executed" ([19.7.4](https://www.postgresql.org/docs/17/runtime-config-query.html#GUC-PLAN-CACHE-MODE)); measured `SHOW plan_cache_mode` = `auto`. Every plan the probe printed shows literals (`dealership_id = '0000…d1'::uuid`, `stocked_on <= '2026-08-04'::date`), i.e. custom plans.

- `EXPLAIN` options: `ANALYZE` executes the statement; `BUFFERS` defaults to off in 17 and must be asked for; `GENERIC_PLAN` cannot be combined with `ANALYZE`; `SERIALIZE` (new in 17) adds output-conversion time ([EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html)). All five statements are `SELECT`s, so `ANALYZE` has no side effects and needs no `BEGIN … ROLLBACK`. Running the dashboard's three statements outside its `REPEATABLE READ, READ ONLY` transaction (`dashboard.query.ts:48-84`) does not change their plans; isolation level is not a planner input.

## 2. Seeding at 20,000 per dealership

- **Time.** `SEED_VEHICLES_PER_DEALERSHIP=20000 node db/seed.ts` on an empty, migrated database: **3.7 s** wall clock (argon2id hashing of three passwords included). Each dealership is one set-based `INSERT … SELECT generate_series` (`apps/api/db/seed.ts:63-96`) plus three action rounds (`seed.ts:102-125,171-173`).
- **Rows (measured).** Per dealership 20,001 vehicles: 16,020 `IN_STOCK`, 2,000 `RESERVED`, 1,981 `SOLD` (the re-acquired VIN adds one `IN_STOCK`; rows with age < 2 that would be `SOLD` stay `IN_STOCK`, `seed.ts:82`). Actions: London 6,126 on 3,501 vehicles, New York 6,962 on 3,979 (lower thresholds, 45/75), Sydney 6,126 on 3,501; 19,214 in total. That is 40% of the in-stock Aging set (London: 8,752 Aging, `rn % 5 IN (0,2)`, `seed.ts:114`), so actions scale with the vehicle count.
- **Gotcha: seed into an empty database.** Actions are seeded only for a dealership that has none yet (`seed.ts:166-170`). Measured on a second database: default seed (250), then `SEED_VEHICLES_PER_DEALERSHIP=20000` → 60,003 vehicles but only **233 actions** on 135 vehicles. The second run also prints "Nothing to seed" (`seed.ts:199-203` counts new users only), though it added ~59k vehicles. The README must say to start from an empty volume (`docker compose down -v`).
- **Statistics.** Right after seeding, `pg_stat_user_tables.last_autoanalyze` was empty for both tables; autovacuum analyzed them within about a minute (defaults measured: `autovacuum_naptime` 1 min, `autovacuum_analyze_threshold` 50, `autovacuum_analyze_scale_factor` 0.1; formula "analyze base threshold + analyze scale factor × number of tuples", [24.1.6](https://www.postgresql.org/docs/17/routine-vacuuming.html#AUTOVACUUM)). The EXPLAIN docs: "if a table has recently had substantial changes in its contents, you might need to do a manual `ANALYZE` rather than wait for autovacuum" ([EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html)). A script run straight after the seed would race autovacuum, so it should run `ANALYZE vehicle, vehicle_action` first (cheap on 60k + 19k rows).
- **The seed is heavier than the target, and shaped differently.** 16,020 in-stock per dealership is 8× the design's maximum of 2,000 (`backend-architecture.md:71`), so timings are conservative. But with only three dealerships, one dealership is a third of `vehicle`, whereas at the sized 50 dealerships it would be about 2%. This changes the base-scan choice for the list (below); the design's shape is not reproduced by the seed. Not measured with more dealerships.

Observations (not changes asked for by #15):

- **The list does not use `vehicle_dealership_status_stocked_idx` at this seed.** Alone, the same `WHERE` picks a Bitmap Index Scan on it (cost 1,657 vs Seq Scan 2,002, measured). Inside the list, the `LATERAL` estimate (16,162 × 10.36 ≈ 167k) dwarfs the scan, so both outer paths cost within 1% and the planner keeps the one with the lower startup cost, the Seq Scan. This is an inference from the costs, consistent with the planner's fuzzy path comparison (`STD_FUZZ_FACTOR` 1.01 in `src/backend/optimizer/util/pathnode.c`, not read for this note). The real cost difference is a few ms (Seq Scan 6.3 ms vs Bitmap ~1.8 ms). The README should show the plan as it is and say why.
- **The list's cost is the `LATERAL` on every matching row, not the page.** `count(*) OVER ()` and `ORDER BY` sit above the join, so the latest action is looked up for all 16,020 rows before the limit. Linear in in-stock count: about 45 ms at 16k, so about 6 ms at 2,000. Fine for the target; noted for §6 (keyset pagination) if it ever matters.
- **JIT fires** on three statements because the over-estimated `LATERAL` cost passes `jit_above_cost` (100,000, measured; `jit` on), adding 5–12 ms each. Worth a line in the README; turning it off is a tuning decision outside #15.
- **The 300 ms target holds** with large margin: the worst service call (dashboard, three statements) is 65.7 ms p95 at 8× the target's row count.

## 4. Script or hand-run psql

- **Hand-run psql with pasted SQL** keeps nothing in the repo, but the SQL is a copy: `todayLocal`, the `stocked_on` bounds from `toStockedOnBounds` (`inventory/domain/aging-policy.ts:40-64`) and the dealership's thresholds must be computed by hand each day, and a later change to `vehicles.service.ts` or `dashboard.query.ts` makes the README evidence stale without anything failing.
- **A committed script** that calls the real service methods with a capturing drizzle logger and re-sends each `SELECT` as `EXPLAIN (ANALYZE, BUFFERS)` with the same params is faithful by construction and reproducible with one command. The repo has the precedent: `src/export-openapi.ts` is built by `nest build` and run from `dist` (`apps/api/package.json` `openapi:export`), and is excluded from coverage (`apps/api/vitest.config.ts:28`). It cannot live under `apps/api/db/`: those scripts run with type stripping and import packages only (ADR 0009, `seed.ts:2`), and the services use decorators and `.js` relative imports that need the build. Constructing the services directly (`new VehiclesService(db, clock)`, `new DashboardService(db, clock)`) works without Nest DI (probe); the `DealershipContext` can be read with one query (`timezone`, thresholds, `(now() AT TIME ZONE timezone)::date`), so time-zone maths stays in Postgres.
- The script's own output (plans) is what the README pastes, with the command, the date, Postgres version and the note that timings are machine-dependent. No drift test: timings and dates change on every run.

## Decisions

1. Capture the plans with a small committed script `apps/api/src/explain-queries.ts`, run as `pnpm --filter @inventory/api db:explain` (`nest build && node dist/explain-queries.js`), excluded from coverage like `export-openapi.ts`. Recommend: yes, over hand-pasted psql SQL.
2. The script builds a `drizzle({ client: pool, logger })` that records `(text, params)`, calls the real `VehiclesService.list` and `DashboardService.get`, and re-sends each recorded `SELECT` as `EXPLAIN (ANALYZE, BUFFERS) <text>` with the same params through `pg`. Recommend: yes; it gets the app's exact SQL and the same custom plan without touching the services.
3. Do not use `auto_explain`, `log_statement` or a compose override for the README. Recommend: skip; they need server config and superuser, and add log noise, for no gain over (2).
4. Plan four list cases (default `IN_STOCK` oldest limit 50; `tier=AGING`; `make`+`model`; `tier=AGING&hasAction=false`) and the dashboard's three statements, for one dealership (London). Recommend: yes.
5. Run `ANALYZE vehicle, vehicle_action` at the start of the script, and one warm-up call before each `EXPLAIN`. Recommend: yes; right after a seed, autoanalyze has not run yet.
6. The README procedure seeds `SEED_VEHICLES_PER_DEALERSHIP=20000` into an **empty** database (`docker compose down -v` first). Recommend: yes; a re-seed over the default 250 leaves only 233 actions.
7. Fix `docs/environment-setup.md:34`, which says `SEED_VEHICLES_PER_DEALERSHIP=2000` for `EXPLAIN ANALYZE`, to `20000` and the empty-database note, matching §4.14 (`backend-architecture.md:522`). Recommend: yes, in the same PR.
8. Show the plans as they are (Seq Scan on the list at this seed, JIT lines) with one sentence each on why, and state that the seed has 16,020 in-stock vehicles per dealership (8× the target) over three dealerships. Recommend: yes; no index or JIT tuning in #15.
9. No ADR: this is tooling and evidence, not a design decision. Recommend: none, unless the script is judged a new pattern beyond `export-openapi.ts`.
