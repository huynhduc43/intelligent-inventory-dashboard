# Vehicle actions building blocks (research for #11)

Research for issue #11 (§4.7, §4.9, D4, D5, D19, P2, P3, ADR 0012). The routes, the append-only table, the `INSERT … SELECT … WHERE status = 'IN_STOCK'` write and the re-read on 0 rows are taken as given; this note only checks how the pieces behave. Five findings shape the design. (1) RFC 9110 says the `Location` of a 201 "refers to the primary resource created", and a 201 without `Location` means the target URI is the created resource. Pointing `Location` at the collection therefore says the wrong thing. A URI with no `GET` handler is allowed but is a weak identifier. (2) Under READ COMMITTED the `SELECT` inside the insert is a plain read: it neither waits for nor re-checks a concurrent reserve or sell, and it sees the last committed row. The composite FK check takes `FOR KEY SHARE` on the vehicle, which does not conflict with a status-only `UPDATE` (`FOR NO KEY UPDATE`). Two concurrent inserts for one vehicle both succeed without waiting. The window that remains (an action inserted while a reserve is in flight) is equivalent to the serial order "action, then reserve" and is not a correctness bug. `FOR SHARE OF v` closes it if wanted. (3) Identity values in `INSERT … SELECT … ORDER BY` follow the sort order in practice (the plan evaluates `nextval` above the `Sort`), but no documentation guarantees it. Separate statements do get increasing ids, because `CACHE 1` makes `nextval` sequential. (4) The question's premise is out of date: since zod 4.5.0, `z.string().max(n)` counts **code points**, the same unit as Postgres `char_length` in a UTF8 database. `z.string().max(1000)` matches `vehicle_action_note_chk` exactly. A NUL character in the note is a different trap: Postgres rejects it with `22021`, and the filter turns that into a 500. (5) A Nest `@Post` defaults to 201, and `@Res({ passthrough: true })` with `res.location(url)` sets a dynamic `Location` while Nest still serialises the returned body.

Method: claims were checked against RFC 9110 (rfc-editor.org), the PostgreSQL 17 docs, the PostgreSQL source at `REL_17_STABLE` ([`25b5578`](https://github.com/postgres/postgres/tree/25b55788d89d47d558c282a8e62d474d0c804ee9)) where the docs are silent, zod.dev and the zod 4.5.0 release notes, docs.nestjs.com and expressjs.com, and the installed packages in `apps/api/node_modules` (`zod@4.6.7`, `@nestjs/core`, `@nestjs/common` and `@nestjs/platform-express@12.3.2`, `express@5.3.0`, `pg@8.23.1`). The probes were throwaway scripts kept outside the repo (scratchpad). They ran against a separate `postgres:17.11-alpine` container (server encoding UTF8) with the committed migrations applied, using concurrent `psql` sessions and the `pgrowlocks` extension. Line numbers refer to the installed package files of the version named, or to the PostgreSQL commit above.

## 1. `Location` on a 201 (RFC 9110)

- **What it must identify.** For POST: "If one or more resources has been created on the origin server as a result of successfully processing a POST request, the origin server SHOULD send a 201 (Created) response containing a Location header field that provides an identifier for the primary resource created" ([§9.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.3)). For the header: "For 201 (Created) responses, the Location value refers to the primary resource created by the request" ([§10.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.2)). The status code: "The primary resource created by the request is identified by either a Location header field in the response or, if no Location header field is received, by the target URI" ([§15.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.2)).
- **Pointing at the collection.** The target URI of `POST …/vehicles/{v}/actions` is the collection. Under §15.3.2, sending `Location: …/actions` has the same meaning as sending no `Location` at all: it says the collection is the resource that was created. That is false, so it is wrong, not just weak. A fragment (`…/actions#42`) is not the way out either: "the Location header field in a 201 (Created) response is supposed to provide a URI that is specific to the created resource", and §10.2.2 gives this as a case where a fragment "would not be appropriate".
- **A URI with no `GET` handler.** RFC 9110 does not require the identifier to be dereferenceable: "Anyone can mint a URI, whether or not a server exists and whether or not that server currently maps that identifier to a resource" ([§4.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.2)), and "HTTP does not limit the nature of a resource" ([§3.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-3.1)). `…/actions/{id}` therefore satisfies §10.2.2 even if the server never routes it. The cost is that a client following it gets 404, which §15.5.5 defines as "did not find a current representation for the target resource" ([§15.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.5)). That is accurate, but it is unhelpful for a resource the server just reported as created. A 405 would be wrong, because it requires an `Allow` header listing the methods the resource supports ([§15.5.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.6)). `GET` and `HEAD` are mandatory for "general-purpose servers", not for each resource ([§9.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.1)).
- **The body.** The 201 response "SHOULD" carry "a representation that describes the status of the request while referring to the new resource(s)" (§9.3.3), and "typically describes and links to the resource(s) created" (§15.3.2). Returning the created action, as §4.7 says, meets both.
- **Relative or absolute.** `Location = URI-reference`, and a relative reference is resolved against the target URI (§10.2.2). The absolute path `/dealerships/{d}/vehicles/{v}/actions/{id}` is unambiguous. The app sets no global prefix (`setGlobalPrefix` is not used in `apps/api/src`), so the path is the route path.
- **Options** (Q1): A. `Location: …/actions/{id}` with no handler (a `GET` on it is 404). B. The same `Location`, plus `GET …/actions/{id}`, a single-row read with the same permission and the same `dealership_id` filter. C. `Location: …/actions` (the collection). C contradicts §10.2.2 and §15.3.2.

## 2. The action insert under READ COMMITTED

Statement checked (the design's write, P2):

```sql
INSERT INTO vehicle_action (vehicle_id, dealership_id, action_type, note, created_by)
SELECT v.id, v.dealership_id, $type, $note, $user
FROM vehicle v
WHERE v.id = $v AND v.dealership_id = $d AND v.status = 'IN_STOCK'
RETURNING id;
```

- **The `SELECT` part is a plain read.** "a `SELECT` query (without a `FOR UPDATE/SHARE` clause) sees only data committed before the query began; it never sees either uncommitted data or changes committed by concurrent transactions during the query's execution" ([13.2.1](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)). The wait-and-re-check rule on the same page ("the would-be updater will wait for the first updating transaction … The search condition of the command (the `WHERE` clause) is re-evaluated") applies only to the target rows of "`UPDATE`, `DELETE`, `SELECT FOR UPDATE`, and `SELECT FOR SHARE`". The `vehicle` row here is a source row, not a target, so it is not re-checked. Row locks also do not block it: "Row-level locks do not affect data querying; they block only _writers and lockers_ to the same row" ([13.3.2](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)).
- **The FK check takes `FOR KEY SHARE`.** The docs do not say which lock an FK check takes. The source does: `RI_FKey_check` builds `SELECT 1 FROM [ONLY] <pktable> x WHERE pkatt1 = $1 [AND ...] FOR KEY SHARE OF x` and opens the referenced table in `RowShareLock` "since that's what our eventual SELECT FOR KEY SHARE will get on it" ([`ri_triggers.c` L268-L273, L360-L389](https://github.com/postgres/postgres/blob/25b55788d89d47d558c282a8e62d474d0c804ee9/src/backend/utils/adt/ri_triggers.c#L268-L389)). In READ COMMITTED it runs with "an up-to-date regular snapshot" (same file, [L2373-L2394](https://github.com/postgres/postgres/blob/25b55788d89d47d558c282a8e62d474d0c804ee9/src/backend/utils/adt/ri_triggers.c#L2373-L2394)), so it checks the latest committed version of the row, not the statement's snapshot. `vehicle_action` has three FKs (`vehicle (id, dealership_id)`, `dealership (id)`, `app_user (id)`), so one insert key-share-locks three rows. Probe, with an insert's transaction left open: `pgrowlocks` showed `{"For Key Share"}` on the vehicle, the dealership and the user rows. `pg_locks` showed `RowShareLock` on `vehicle`, `dealership` and `app_user`, and `RowExclusiveLock` on `vehicle_action` and `vehicle_action_id_seq`.
- **A status-only `UPDATE` does not conflict with it.** An `UPDATE` takes `FOR UPDATE` only if it modifies "columns … that have a unique index on them that can be used in a foreign key (so partial indexes and expressional indexes are not considered)". Every other `UPDATE` takes `FOR NO KEY UPDATE`, which "will not block `SELECT FOR KEY SHARE`". A key-share lock "blocks other transactions from performing `DELETE` or any `UPDATE` that changes the key values, but not other `UPDATE`" ([13.3.2](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS); Table 13.3 marks `FOR KEY SHARE` as conflicting only with `FOR UPDATE`). For `vehicle`, the key columns are `id` (primary key) and `(id, dealership_id)` (`vehicle_id_dealership_uq`). `vehicle_dealership_vin_open_uq` is partial, so it does not count. `status` and `sold_at` are not key columns, so reserve, unreserve and sell are all `FOR NO KEY UPDATE`. The source agrees: `heap_update` picks `LockTupleNoKeyExclusive` when `!bms_overlap(modified_attrs, key_attrs)`, and it does not wait for "just a key-share locker" when the key is intact ([`heapam.c` L3536-L3569, L3732-L3740](https://github.com/postgres/postgres/blob/25b55788d89d47d558c282a8e62d474d0c804ee9/src/backend/access/heap/heapam.c#L3536-L3740)). In the other direction, `heap_lock_tuple` in `KeyShare` mode does not wait for an in-progress update "if the key hasn't been modified" ([L4996-L5019](https://github.com/postgres/postgres/blob/25b55788d89d47d558c282a8e62d474d0c804ee9/src/backend/access/heap/heapam.c#L4996-L5019)).
- **Probe results** (vehicle `IN_STOCK`; session A holds its change open for 3 s, and session B runs the insert 0.7 s later):

  | Session A, uncommitted                                | Session B's insert                                                                                                      |
  | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
  | `UPDATE vehicle SET status = 'RESERVED'`              | `INSERT 0 1` in 7.8 ms: no wait, it saw the committed `IN_STOCK` row; A then commits → vehicle `RESERVED` with 1 action |
  | (A already committed the reserve)                     | `INSERT 0 0`: the 0-row path → re-read → 409                                                                            |
  | `UPDATE vehicle SET dealership_id = …` (a key column) | waited 2.6 s for A, then `23503` FK violation: the FK check is the part that blocks and re-checks                       |
  | an open action insert (holds `FOR KEY SHARE`)         | a reserve `UPDATE` from B finishes in 1.4 ms: no wait                                                                   |
  | an open action insert for the same vehicle            | `INSERT 0 1` in 2.3 ms; both rows persist (P3)                                                                          |

- **Two concurrent inserts.** Key-share locks are compatible with each other (Table 13.3), and the identity is a sequence. Sequence calls do not wait for other transactions and "are never rolled back" ([CREATE SEQUENCE, Notes](https://www.postgresql.org/docs/17/sql-createsequence.html)). Both inserts succeed, which is what P3 requires. The probe also showed that **id order is `nextval` order, not commit order**: A took id 4 and committed after B, which took id 5. A reader never sees the current action go backwards, because a row that commits later with a lower id is never the newest. But the manager whose insert got the lower id is told "201, now the vehicle's current action" (§4.9) for an action that is already not current. P3 accepts this ("both persist; newest is current").
- **The remaining window.** If the insert's statement snapshot is taken before a reserve or sell commits, the action is inserted, and the vehicle can end up `RESERVED` or `SOLD` with an action whose `created_at` is after `vehicle.updated_at`. This is not a correctness bug. The insert reads `vehicle.status` and the status change does not read `vehicle_action`, so the only dependency runs from the insert to the update. There is no cycle, and the outcome equals the serial order "action logged, then reserved". P2's "A vehicle sold a millisecond earlier can't receive an action" holds where "earlier" means "committed before the insert statement started". It does not hold for a sale that is still in flight. A cosmetic effect remains: in the history, an action can carry a timestamp after the reservation.
- **Closing the window, if wanted** (Q2): append `FOR SHARE OF v` to the `SELECT`. `FOR SHARE` conflicts with `FOR NO KEY UPDATE`, so the insert waits for an in-flight status change and then re-evaluates `status = 'IN_STOCK'` on the new row version (13.2.1, quoted above). Probe: with a reserve open, the insert waited 2.3 s and then returned `INSERT 0 0` (→ 409). Two `FOR SHARE` inserts still ran concurrently (`INSERT 0 1` in 2.4 ms each). The price is that a reserve or sell now waits for an open action insert (probe: 1.3 s, until the insert's transaction ended). A single-statement autocommit insert holds the lock for milliseconds.
- **The 0-row re-read.** The re-read is a second statement with a new snapshot. If the vehicle went `IN_STOCK → RESERVED → IN_STOCK` between the two statements, the re-read sees `IN_STOCK` and the handler still answers 409, for a vehicle that is in stock again. That is rare and harmless (a retry succeeds), but the 409 branch should not assert that the status it read differs from `IN_STOCK`.
- **`created_at`.** The column defaults to `now()`, which is "the start time of the current transaction" ([9.9.5](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)). ADR 0002 sets `updated_at` from the injected `Clock`. Passing `Clock.now()` as `created_at` keeps D19's audit time testable and consistent with it. Under concurrency, neither source makes `created_at` order match id order, which is why "current" stays "newest by `id`".

## 3. Identity order in `INSERT … SELECT … ORDER BY`

- **Not documented.** The INSERT page says only that an identity column "will be filled with a new value generated by the associated sequence" and that `query` is "A query (`SELECT` statement) that supplies the rows to be inserted" ([INSERT](https://www.postgresql.org/docs/17/sql-insert.html)). It says nothing about the order of rows or of generated values. The SELECT page does document that "PostgreSQL will effectively evaluate output expressions after sorting and limiting, so long as those expressions are not referenced in `DISTINCT`, `ORDER BY` or `GROUP BY`" ([SELECT, SELECT List](https://www.postgresql.org/docs/17/sql-select.html#SQL-SELECT-LIST)). But an identity default is not one of the `SELECT`'s output expressions. The rewriter adds it to the `INSERT`'s own target list.
- **Observed and explained by the source.** `EXPLAIN VERBOSE` of `INSERT INTO t (k, created_at) SELECT … FROM generate_series(1,5) n ORDER BY n DESC`:

  ```
  Insert on pg_temp.t
    ->  Subquery Scan on "*SELECT*"
          Output: nextval('t_id_seq'), "*SELECT*".n, …
          ->  Sort
                Sort Key: n.n DESC
  ```

  `nextval` runs in the projection above the `Sort`, so ids came out as `1:5 2:4 3:3 4:2 5:1`, in sort order. The subquery stays a separate scan because `is_simple_subquery` refuses to pull up a subquery that has a `sortClause` ([`prepjointree.c` L1692-L1713](https://github.com/postgres/postgres/blob/25b55788d89d47d558c282a8e62d474d0c804ee9/src/backend/optimizer/prep/prepjointree.c#L1692-L1713)). This is how the planner works today, not a promise. Parallel or batched inserts, or a planner change, could break it without a release note.

- **Safe ways for the seed.**
  - **Separate statements, one per "generation"** (the vehicle-list note's recommendation 14): insert the older action for each chosen vehicle in one statement, then the newer one in a later statement. The identity sequence is `CACHE 1` (`db/migrations/0000_init.sql:50`), and "with a _cache_ setting of one it is safe to assume that `nextval` values are generated sequentially" ([CREATE SEQUENCE, Notes](https://www.postgresql.org/docs/17/sql-createsequence.html)). So every id from the later statement is higher than every id from the earlier one. Give the earlier generation the older `created_at`. Within one statement, each vehicle gets one row, so the order inside the statement does not matter.
  - **`nextval` in the `SELECT` list with `OVERRIDING SYSTEM VALUE`**: `INSERT INTO vehicle_action (id, …) OVERRIDING SYSTEM VALUE SELECT nextval(pg_get_serial_sequence('vehicle_action','id')), … ORDER BY vehicle_id, created_at`. This relies on the documented SELECT-list rule above, and the INSERT page allows explicit values with that clause on a `GENERATED ALWAYS` column ([INSERT, OVERRIDING SYSTEM VALUE](https://www.postgresql.org/docs/17/sql-insert.html)). It works in one statement, but it is unusual SQL for a seed.
  - Idempotency is unchanged: guard the later statement as the vehicle-list note does (`… = 1` existing action), or insert actions only for the `RETURNING` rows.

## 4. Note length: `char_length` and zod

- **Postgres counts code points in UTF8.** `char_length` "Returns number of characters in the string" ([9.4, Table 9.9](https://www.postgresql.org/docs/17/functions-string.html)). The docs do not define "character". The source does: `text_length` calls `pg_mbstrlen_with_len`, which counts one per `pg_mblen` step ([`varlena.c` L711-L724](https://github.com/postgres/postgres/blob/25b55788d89d47d558c282a8e62d474d0c804ee9/src/backend/utils/adt/varlena.c#L711-L724), [`mbutils.c` L1183-L1200](https://github.com/postgres/postgres/blob/25b55788d89d47d558c282a8e62d474d0c804ee9/src/backend/utils/mb/mbutils.c#L1183-L1200)). In UTF8, `pg_utf_mblen` returns 1–4 from the lead byte, so one step is one code point ([`wchar.c` L556-L576](https://github.com/postgres/postgres/blob/25b55788d89d47d558c282a8e62d474d0c804ee9/src/common/wchar.c#L556-L576)).
- **zod 4.5+ also counts code points.** zod.dev: "Length is measured in Unicode code points, not UTF-16 code units. Emoji outside the Basic Multilingual Plane count as one, and combining marks and ZWJ sequences count as several" ([zod.dev/api, Strings](https://zod.dev/api#strings)). The change shipped in [v4.5.0](https://github.com/colinhacks/zod/releases/tag/v4.5.0) ("String length counts code points", [#6441](https://github.com/colinhacks/zod/pull/6441)), which says `.max()` "only loosens". In the installed `zod@4.6.7`, `$ZodCheckMaxLength` uses `util.codePointLength(input)` when `input.length > max` (`zod/v4/core/checks.js:265-287`, `util.js:619`). That function counts a surrogate pair once and a lone surrogate as one. The repo pins `"zod": "^4.6.7"`, so it cannot resolve below 4.5.
- **Probe** (Node `pg` → Postgres 17, UTF8):

  | Input                     | JS `.length` | code points | `char_length`          | `z.string().max(n)` measures |
  | ------------------------- | ------------ | ----------- | ---------------------- | ---------------------------- |
  | `😀`                      | 2            | 1           | 1                      | 1                            |
  | `🇻🇳` (two regional flags) | 4            | 2           | 2                      | 2                            |
  | `é`                       | 2            | 2           | 2                      | 2                            |
  | lone `\ud800`             | 1            | 1           | 1 (stored as `U+FFFD`) | 1                            |

  `z.string().max(1000)` accepted 1,000 emoji (JS length 2,000) and Postgres's `char_length(…) <= 1000` held for the same string. So the API bound and `vehicle_action_note_chk` agree, and no `refine` is needed. On a zod older than 4.5, the idiomatic form would be `z.string().refine((s) => [...s].length <= 1000, …)`. The string iterator yields code points, so it matches `char_length`. A lone surrogate is silently replaced by `U+FFFD` on the way to Postgres (probe: the round trip returned `"�"`). The count still agrees.

- **NUL is the real trap.** `'a\u0000b'` sent as a parameter fails with `22021 invalid byte sequence for encoding "UTF8": 0x00` (probe). JSON allows `"\u0000"`, zod accepts it, and the problem filter maps any non-`HttpException` to `500 INTERNAL` (`apps/api/src/shared/problem.ts:139-143`, used by `problem-details.filter.ts:18-26`). Rejecting NUL in the schema (`.regex(/^[^\u0000]*$/)` or `.refine((s) => !s.includes('\u0000'))`) turns it into a 400 `VALIDATION_FAILED`. The same gap exists for every other free-text input that reaches Postgres. The login schema is one example, and it is out of scope here.

## 5. Nest: 201, `Location` and the body

- **POST defaults to 201.** "The response's **status code** is 200 by default, except for POST requests, which use 201" ([Controllers, Status code](https://docs.nestjs.com/controllers#status-code)). Source: `httpStatusCode = httpCode ?? getStatusByMethod(requestMethod)`, and `getStatusByMethod` returns `HttpStatus.CREATED` for `RequestMethod.POST` (`@nestjs/core/router/router-execution-context.js:109`, `router-response-controller.js:51`). The repo's login uses `@HttpCode(200)` to opt out (`auth.controller.ts:38`). The actions `POST` needs no `@HttpCode`.
- **A dynamic header needs the response object.** `@Header()` takes fixed values. For anything else, "use either the `@Header()` decorator or a library-specific response object (and call `res.header()` directly)" ([Controllers, Headers](https://docs.nestjs.com/controllers#response-headers)). Injecting `@Res()` normally hands the whole response to the handler. `passthrough: true` keeps Nest's standard handling: "To combine them (for example, to inject the response object only to set cookies or headers while leaving the rest to the framework), set the `passthrough` option to `true`", and it restores "interceptors and the `@HttpCode()` / `@Header()` decorators" ([Controllers, Library-specific approach](https://docs.nestjs.com/controllers#library-specific-approach)). Source: `isResponseHandled` is true only when `@Res()`/`@Next()` is present **and** passthrough is off (`router-execution-context.js:336-340`). Nest sets the status before calling the handler (`:69`) and afterwards replies with the returned value (`express-adapter.js:90-96`). So headers set in the handler survive, as does `Cache-Control` from `@Header()`, and the 201 stays.
- **`res.location` vs `res.setHeader`.** Express 5's `res.location(url)` is `this.set('Location', encodeUrl(url))` (`express/lib/response.js:797-799`). It percent-encodes the URL "if not encoded already" and does no other validation ([Express 5 API, res.location](https://expressjs.com/en/5x/api/response#res.location)). Built from two UUIDs and a bigint, the path needs no encoding, so `res.location(path)` and `res.setHeader('Location', path)` give the same header. `res.location` names the intent.
- **Shape that follows the repo** (ADR 0005, `auth.controller.ts:24-27, 66`): the body is a module-level `z.strictObject` passed as `@Body({ schema })`, and the handler types it with `z.infer`. The global `StandardSchemaValidationPipe` (`shared/shared.module.ts`) validates it and maps issues to `400 VALIDATION_FAILED` with RFC 6901 pointers. Unknown keys are rejected. The `vehicleId` path parameter follows `vehicles.controller.ts:182-191`: a plain `@Param('vehicleId')`, with `UUID.test` → `NotFoundException`, so a malformed id is a 404 and never a Postgres `22P02`.

  ```ts
  const createActionSchema = z.strictObject({
    actionType: z.enum(ACTION_TYPES),
    note: z.string().max(1000).refine((s) => !s.includes('\u0000'), 'Must not contain NUL').optional(),
  });

  @Post()
  @RequirePermission('vehicle_action:create')
  async create(
    @Req() req: AuthedRequest,
    @Param('vehicleId') vehicleId: string,
    @Body({ schema: createActionSchema }) body: z.infer<typeof createActionSchema>,
    @Res({ passthrough: true }) res: Response, // import type { Response } from 'express'
  ) {
    if (!UUID.test(vehicleId)) throw new NotFoundException('Resource not found.');
    const { id, ctx } = context(req);
    const action = await this.actions.log(id, ctx, vehicleId, body);
    res.location(`/dealerships/${id}/vehicles/${vehicleId}/actions/${action.id}`);
    return action;
  }
  ```

  `@types/express` is already a dev dependency, and `problem-details.filter.ts` already imports `Response` from `express`.

## Questions

**Q1. What `Location` points at.** A. `…/actions/{id}` with no route (a `GET` on it is 404). B. `…/actions/{id}` plus a small `GET …/actions/{id}` (one-row read, `vehicle_action:read`, `dealership_id` and `vehicle_id` in the `WHERE`). C. The collection `…/actions`. Recommendation: A. It is what RFC 9110 §10.2.2 asks for and needs no route that §4.7 does not list. B is a cheap upgrade if the frontend or the tester wants to follow the link. C contradicts §15.3.2.

**Q2. The in-flight reserve window.** A. Keep the design's plain `INSERT … SELECT` and accept that an action can land as a reserve or sell commits (serially equivalent to "action, then status change"). B. Add `FOR SHARE OF v`, so the insert waits for an in-flight status change and then sees the new status (→ 409). Recommendation: A. It matches the design as written and is correct. B is a one-clause change if D5 is read strictly ("never an action on a vehicle that ends up not in stock at commit time"). Both keep P3, because concurrent inserts still both succeed.

**Q3. `created_at` source.** A. Pass `Clock.now()` as a parameter, like `updated_at` (ADR 0002). B. Keep the column default `now()`. Recommendation: A. Tests can pin it, and it is consistent with the other audit column. Ordering stays by `id` either way.

## Recommendations

1. Send `201` with `Location: /dealerships/{d}/vehicles/{v}/actions/{id}` for the created action and return the action as the body; never point `Location` at the collection or use a fragment (Q1 A).
2. Rely on Nest's POST default for the 201 (no `@HttpCode`), and set `Location` with `@Res({ passthrough: true }) res` and `res.location(…)`.
3. Validate the body with a module-level `z.strictObject` through `@Body({ schema })`, following login and ADR 0005; treat a malformed `vehicleId` as 404 with the guard's `UUID` regex, as the vehicle detail route does.
4. Use `z.string().max(1000)` for `note` as is: in zod ≥ 4.5 it counts code points, the same unit as `char_length` in `vehicle_action_note_chk`. No `refine` is needed for length.
